# 技术方案：本地挂载运行时（Ubuntu）—— 一个外部执行工具

- 日期：2026-11-01
- 状态：**方案稿，待评审**。未写实现代码。
- 决策输入（需求方）：
  - 正常 DSH **不走**这条路；它是一个**本地 Ubuntu**，**需要时才向用户申请使用**
  - **工程化上把风险排掉**
  - **不做独立 App**（2026-11-01 明确）
  - Android 因此获得额外的**挂载能力**，而**基本能力仍与 iOS 对齐**

---

## 0. 一句话

**把「本地 Ubuntu」做成一个按 session 申请、用后即弃的外部执行工具——Agent 需要时把一条命令交过去、拿回结果。DSH 本身不在里面跑。**

它不能阻止同 UID 的代码读取内部状态——但它能被做得让**走 `open()` 的那条路**成为一次「有意识的行为」，且**这次行为会被记录和上报**。不走 `open()` 的读法（预开 fd、`/proc/<pid>/fd`）不在这句话的覆盖范围内，见 §2 的残余声明。

---

## 0.1 它不是什么（三条，先划掉）

1. **不是「在 Ubuntu 上重新构建 DSH」。** DSH 整个跑在它现有的地方（WebView 里的 Worker + 宿主加速器），
   一个字节都不搬到 Ubuntu 里。Ubuntu 只是**被执行请求的另一边**。
2. **不是第二个执行域。** 主任务——回合、工具调用、会话、WAL、UI——全部在 DSH 里，与 iOS 基线完全一致。
   出事的只有一条命令的**执行地点**。
3. **不是常驻。** 平时不存在、不运行、不挂载；没有任务时它对系统零影响。

**所以正确的框架是**：

```
主任务（回合、上下文、工具编排、会话状态）  →  DSH，与 iOS 一致，不变
某一类任务（需要完整 Linux 用户态）        →  交给 Ubuntu，拿回 stdout + 产物文件
```

**这也决定了命名**：它不叫 `build.*`——那会让人以为要构建什么。它叫 `ubuntu.exec`，
语义是「把这条命令交给本地 Linux 环境执行」。

## 0.2 资源与耗电：比常驻好在哪，以及哪里**不**更好

需求方问过这一条，答案分三种负载看，**结论不同**。

### 待机——**要拆成三档**（审计指出原来那张表与 §3 第 0 层自相矛盾）

原来这里只有一行「进程 0 / 内存 0 / 唤醒 0，严格更好，差距数量级」。**那是「已关闭」态的数字**，
而 §3 第 0 层推荐的是「**暖着但密封**」（`IdleSealed`）——那个状态**进程和 RSS 都常驻**。

| 档 | 进程 | 内存 | 唤醒 | 与常驻 Ubuntu 比 |
|---|---|---|---|---|
| **未启动**（没进过 `ubuntu`） | **0** | **0** | **0** | **严格更好，数量级** |
| **空闲密封**（session 内、两个 job 之间） | 1（guest 用户态） | 常驻 RSS + 页缓存 | 低（省掉 ptrace 循环与定时器） | **更好，但不是数量级** |
| 关闭中 | 收割中 | 释放中 | —— | —— |

**「严格更好、差距数量级」只许出现在第一行。** 第二行是「暖着」的代价，而它换的是冷启动延迟——
§3 第 0 层已经论证过这笔交易值得，**但不该把它算成零成本**。

### 活跃（正在跑一个 job）

| | 常驻 Ubuntu | 本方案 |
|---|---|---|
| 单次任务开销 | 省掉启动 | **每次付一次冷启动**（挂载 + 用户态拉起） |
| 页缓存 | rootfs 的页已经在缓存里 | **上一个 job 的缓存被挤掉**，每次重新从闪存读 |
| 连续多次任务 | 越跑越省 | **每次都付全额** |

**这一档本方案更差。** 而且方案 §6 明确写了**不做增量、缓存、常驻**——这不是疏忽，是为了不让自己慢慢滑回常驻形态。**代价就是每次冷启动。**

### 磁盘

| | 两个方案 |
|---|---|
| rootfs 占用（约 1–1.5 GB） | **完全一样** |

**按需挂载一点也不省磁盘。** 如果省磁盘是目标，这个方案帮不上——只有「装/不装」这个开关能省。

### 所以结论是

**资源不是本方案的理由，暴露窗口才是。**

- 如果只比**待机耗电**：按需严格更好，**而且这一档正好是手机 99% 的时间**
- 如果只比**单位任务成本**：常驻更好，**任务越密常驻越划算**
- 本方案真正不可替代的理由是 §3 第 1 层：**常驻意味着授权一次、暴露永久**，而这是评审否决原方案的核心那条。资源只是顺带的收益。

**如果将来发现任务频率高到冷启动成本不可接受，正确的解法不是偷偷加常驻**（那会走回被否决的形态），而是**重新评审**：要么承认接受常驻的暴露，要么换一个根本不同的方案。

## 1. 要保护什么

`spec/v1/channel.md:262` 规定执行面（`bash` / `python3` / `git`）对三处内部状态收到 `EACCES` 且**永远看不到字节**：

```
/dsh/home/sessions/
/dsh/home/storages/
/dsh/home/tool-journal/
```

**关键事实**：这个 `EACCES` 是 **Worker 的 VFS 层（JavaScript）**强制的，**不是 Android 内核强制的**。任何不经过 Worker VFS 的执行面都在这个执法点之外。

---

## 2. 诚实的边界声明

**在同一个 App 内，同 UID 的代码无法被阻止读取本 App 的任何文件。** 这是 Android 的进程模型，不是实现缺陷。

所以本方案**不声称「构建代码读不到内部状态」**。它声称的是三件更小的事：

| 声称 | 强度 |
|---|---|
| **意外读取被阻止**（`gcc` / `make` / `find /` / 构建脚本里的 glob） | **强**（挂载表只含工作区） |
| **经 `open()` 的有意读取必须先显式恢复权限**（不是顺手 `cat`） | **中**（只覆盖 `open()` 这条路；见下面的残余声明） |
| **这次 `chmod`（以及直接打开密封根目录）会被记录并上报给用户** | **中**（watch 挂在三个根的父目录上、非递归：根**内部**文件的 `open()` 不产生事件） |

**「有意读取必须可观察」这条只覆盖「`chmod` 密封根」和「直接打开根目录」两种动作。** 读根内部的文件（普通 `open()` 也一样）不产生本层的 watch 事件（见 §3 第 4 层）；下面两种读法**连 `open()` 都没有**，L60 在 API 35 上实测为零事件：

| 读法 | 机制 | 绊线看到什么 |
|---|---|---|
| **预开 fd**：同 UID 进程先 `exec 9<file`，再 `chmod 000` 目录，然后 `cat <&9` | 权限只在 `open()` 时检查；fd 已打开，之后读字节不再经过权限位 | **零**：窗口内没有 `open`、没有 `chmod` → 没有 `IN_OPEN`、没有 `IN_ATTRIB` |
| **`/proc` 读取**：同 UID 的另一进程 `cat /proc/<持有者 pid>/fd/<n>` | 读的是持有者的 fd 表，跨过目录检索权限 | **零**：没有落在密封根上的 `open()`/`chmod` |

第二条恰好落在会话 / 存储 / journal 文件最密集的地方（本 App 自己的 fd 表）。**能做的一条缓解是让子进程不继承 fd**：`ShellJobLauncher` 起 job 前，平台的 `ProcessBuilder` 会关闭子进程里所有 >2 的 fd——L60 设备实测，一个没有 `O_CLOEXEC` 的 `Os.open` fd 不出现在 job 的 `/proc/self/fd` 里（只有 job 自己的 stdio）。**这只关掉「继承」这一半；`/proc/<app-pid>/fd` 那一半关不掉**：读的是持有者进程的 fd 表，子进程清扫无能为力。它是本设计的**残余风险**，不是已缓解项。

**剩下的那条不能排掉的风险，写在这里，也要写进同意文案**：

> 一个恶意依赖可以在构建期间读取本 App 的会话、存储与工具日志，而构建通常需要联网。
> **我们能做的是让这件事留下痕迹，不是让它不可能发生。** 这句只在读的人走了一次 `open()` 时成立；
> 预开 fd 与 `/proc` 读取**连痕迹都没有**。

## 3. 工程对策：四层，逐层降低暴露

### 第 0 层：环境可以暖着，但**密封跟 job 走**

需求方 2026-11-01 追加：**「需要时启动，用完关掉，下次再用再启动；Agent 自己决定什么时候关，或超时自动关。」**

这条要采纳，但**要把「环境生命周期」和「密封生命周期」拆开**——这是整个方案里最重要的一次解耦：

```
环境生命周期    : 启动 → (可能跨多个 job) → 关闭
密封生命周期    : 每个 job 单独：seal → job → restore
```

**为什么必须拆开**：

- 如果两者绑在一起，要么**每个 job 都冷启动**（我原来的方案，成本高），要么**环境活着就一直能读内部状态**（暴露窗口被拉长）
- 拆开之后：**环境可以暖着避免冷启动，但两个 job 之间的空档期内部状态是密封的**

**所以正确的状态机是**：

| 状态 | 环境 | 内部根 | 能读内部状态吗 |
|---|---|---|---|
| 未启动 | 无 | 正常 | 不适用（没有 guest） |
| **空闲**（已启动、没有 job） | 活着（暖） | **密封（chmod 000）** | **不能**（除非刻意 chmod） |
| 跑 job | 活着 | 密封 | 同上 |
| job 之间 | 活着 | **密封** | **不能** |
| 关闭中 | 收割进程树 | 恢复 | —— |

**「暖着但密封」是这个方案能同时拿到低延迟和低暴露的唯一形态。**

### 第 1 层：按 session 申请（不是常驻）

- Ubuntu 环境**默认不挂载**。日常 DSH 完全走 iOS 那条路（WASI 垫片 + 宿主加速器）。
- 有任务需要时，Agent **提出申请** → 用户**审批一次** → **只对这一次 job 生效**。
- **授权按 session**（需求方 2026-11-01 定）：一次批准，**本 session 内**的后续 job 免批。
  - **代价明说**：一次批准覆盖 N 个 job「能读到什么」的授予。评审曾据此反对按 session 授权
    （「运行时持久、授权短暂，授权比后果更窄」）——**需求方权衡后接受**，理由是逐次弹窗在实践中
    会退化成反射性通过，那比一次有意识的批准更差。
  - **补偿**：**每个 job 仍然单独密封 + 单独绊线**，所以用户拿到的是**逐 job 的可见性**。
  - **失效**：session 结束授权立即失效；用户可随时在本 session 内撤销，撤销后下一次
    `ubuntu run` 重新申请。
  - **撤销的实现状态（L60 审计，未落地）**：`UbuntuApproval.revoke()` 有 API，但**零 UI 调用点**。
    构建里实际能清掉授权的只有两条路：停掉本地引擎（`onStop → endSession()`，session 一起结束）
    和销毁 Activity（`onDestroy`）。也就是说「**用户可随时撤销**」目前**没有入口**——
    缺的是 `:lib`「开发者工具」索引的第 7 行（`SettingsSurfaces.kt` 的 `DevTool` 表现有 6 行），
    以及 `:app` 把该行接到 `UbuntuApproval.revoke()` 的 action（`HostShell.kt` 的 `PdshHostAction` 分支）。
    在这两件落地之前，本层只承诺「session 结束授权失效」，不承诺「用户随时可撤销」。

### 第 2 层：挂载表只含工作区

- guest 的根视图 = 一个临时根，里面**只 bind 工作区**
- 内部三个根**不在**挂载表里
- **作用**：构建工具的正常遍历（`find /`、`rg --files /`、包管理器的全盘扫描）看不到它们
- **局限**：proot 是 ptrace 路径翻译，未命中的路径落到真实文件系统。**这一层挡意外，不挡有意**

### 第 3 层：构建期间「密封」内部根（新增，本方案的核心对策）

**观察**：构建 job 在跑的时候，DSH 只是**在等**——它不需要读那三个根。

所以：

```
job 开始 → chmod 000 三个内部根 → 跑构建 → job 结束 → 恢复权限
```

**这一层把「顺手 cat 一下」变成「走 `open()` 就得先 chmod 恢复权限」**：

- 对**意外读取**：从「可读」变成「不可读」，且失败会明确（`EACCES`）
- 对**有意读取**：仍然可以（同 UID 是 owner），但**走 `open()` 这条路必须先显式 chmod** —— **这条路会留痕**。
  它**不是**「有意读取一定会留痕」：预开 fd 与 `/proc/<pid>/fd` 读取既不 chmod 也不 open，什么事件都不产生
  （§2 的残余声明）。**知道 fd 语义的读法不需要那一次 chmod。**

**必须验证的前提**（如果这条不成立，第 3 层作废）：

1. `chmod 000` 之后，同 UID 的进程**对新的 `open()` 确实读不到**（POSIX 权限位对 owner 也生效）；
   **已经打开的 fd 不受影响**（L60 实测）
2. **DSH 在 job 期间确实不需要读那三个根**——如果它需要（比如要流式展示日志），密封会打断它
3. 权限恢复是**幂等的**，且**进程被杀后能被下次启动修复**（否则一次崩溃会让内部根永久 000）

第 3 条是这一层最大的工程风险，**必须有单独测试**：模拟 job 中途进程被杀，下次启动检测并修复权限。

### 第 4.5 层：谁来关

**方向不对称：Agent 可以关，但不能「不关」。**

这个不对称是对的，因为两个方向的代价差一个量级：

| 方向 | 代价 |
|---|---|
| **关早了** | 下一次多一次冷启动。**便宜，可恢复** |
| **关晚了** | 环境继续活着，内部状态持续可读。**贵，且不可逆** |

所以：

- **Agent 随时可以关**——不需要批准，不需要解释。工具说明里提一句「用完请关闭」即可（需求方 2026-11-01 定）。
- **Agent 不能阻止系统关**。超时到了、App 进后台了、内存压力上来了，系统照关，**Agent 没有否决权**。

关闭权三个来源，**优先级从高到低**：

1. **系统强制**：App 进后台 / 内存压力 / 电量低 → **立即收割并关闭**（或密封 + 冻结）
2. **系统超时**：空闲超过 N 分钟 → 关闭
3. **Agent 主动关**：任何时候，随时生效

**超时值是次要的**——真正的终止来源几乎不会是超时，而是 LMK / Doze / 用户切走。**设计必须能承受非计划死亡**，不能假设能优雅超时。

**「关闭」的定义**（不是杀直接子进程）：

- 杀**整个进程组**（proot 没有 PID namespace，后台 fork 会活过 kill）
- 收割后扫一遍 `/proc`，确认这个 UID 下没有残留进程
- **有残留就上报**，并强制 `kill -9`
- **恢复内部根权限**（哪怕前面步骤失败，这一步必须做）

### 第 4 层：绊线（检测 + 上报）

**密封能被绕过，所以要能知道它被绕过。**

- 在三个内部根的**父目录**上挂 `FileObserver`（`IN_OPEN` / `IN_ATTRIB` / `IN_ACCESS`）
- job 期间任何访问 → 记进 job 的审计
- job 结束时，`ubuntu.status` 多一个字段：**`internalAccessObserved: true/false`**
- **如果观察到**：同意面上明确告诉用户「这次构建期间，内部状态被访问过」

**局限，明说**：

- `FileObserver` 基于 inotify，**可能漏**（watch 数量有限、某些访问路径不触发）
- **预开 fd 与 `/proc/<pid>/fd` 读取不产生 inotify 事件**（L60 实测）：前者没有 `open()`，后者读的是
  持有者的 fd 表。所以 `observed == false` 不等于「没读过」，更不等于「没有通过 fd 读过」。
- **watch 是非递归的**：它只看见「`chmod` 根」和「直接打开根目录」；`cat sessions/x.jsonl` 这类
  根内部的 `open()` 发生在 `sessions/` 自己的 watch 上，本层看不到（`FileObserverTripwireSource` 的注释已承认这条）。
- 它**不阻止**，只报告
- 所以它是「让**走 `open()` 的**行为留下痕迹」，不是「让行为不可能」，也不是「让所有读取都留下痕迹」

## 4. 契约面

### 4.1 `ubuntu.exec` 是宿主工具

| 备选 | 判定 |
|---|---|
| accelerator | ❌ `spec/v1/exec.md:113-117` 只允许 advertised 的**只读** accelerator 以 `0x20` 出行；编译是写 |
| 新 capability 字符串 | ❌ `spec/v1/channel.md:164`：其它 capability 字符串是 **reserved** |
| **宿主工具** | ✅ `spec/v1/bridge.md:177` 有 `[NEW]` 命名先例（`preview.open`、`directory.pick`） |
| 复用 `HandingOff` | ❌ 那是 session 权威的整体转移；这里需要一条更窄的、带结果返回的缝 |

### 4.2 必须异步 JobRef

三条既有约束决定：shell 墙钟 **120 秒**、App 内 WebView 会被挂起（阻塞调用钉死 session）、`Draining` 死线 **20 秒**（`spec/v1/budgets.md`）。

> 下文用 `RUNNING` / `SUCCEEDED` / `ASSET_FAILED` / `SEAL_BROKEN` 等**描述性名字**，不是契约字面量——字面量由 spec PR 定。

`RUNNING` / `SUCCEEDED` / `ASSET_FAILED` / `SEAL_BROKEN` 等是**描述**，命名与枚举值由 spec PR 决定。

```
ubuntu.exec    → JobRef
build.status → 状态 + 有界日志尾（256 KiB，与 shell 输出上限一致）
产物         → 不做新 fetch API，一律经 Worker 走标准 VFS mutation
```

### 4.3 Agent 侧的工具面：一条命令，不是一个新命名空间

Agent 通过 `bash` 工作，`bash` 里是**一张命令表**（`plugins/shell-ext/src/commands.ts` 是生产代码组装它的唯一地方）：

- just-bash 内建
- phone 命令
- **从宿主 HELLO caps 里 advertised 的 accelerator**（未 advertised 的 `rg` 留在 Worker 本地实现，D12）
- WASI 工具箱（`python3` / `jq` / …）

**所以本地 Ubuntu 的入口是一条命令**，与 `rg` / `jq` / `python3` 同类，**不是新的 tool namespace**：

```
ubuntu run --workspace <path> -- <command…>     # 命令本身由 bash 执行，Ubuntu 是它的执行地点
```

**它和 accelerator 的区别**：

| | accelerator | `ubuntu` |
|---|---|---|
| 只读 | ✅（`exec.md:113-117` 强制） | ❌ 它会写 |
| 未 advertised 时 | 回落到 Worker 本地实现 | **命令不存在 → 127 not-available**（诚实：这台设备没有这个能力） |
| 传输 | `0x20` 出行 | **也是 `0x20`（挂在 `phone` 工具目录下）**——见 §4.6 |

**「未 advertised 就 127」这条很重要**：它让「这台设备没有挂载能力」变成一个**诚实的、可观测的事实**，而不是一个超时或一个假成功。这与仓库已有的「被拒绝的 redirect 有可观测面」是同一个纪律。

### 4.3.1 传输的现状：仍然是 `0x20`，§12 的 bridge 没有实现

**这一节的标题原本写着「不出行」，那是错的。** 独立车道查证（L57）：

- Android 全树**没有 page↔host 消息通道**：`grep "addJavascriptInterface|postWebMessage|WebMessageListener"` 只命中
  `WebViewEngine.kt:1176` 的**特性探测**，没有任何 listener 被安装；唯一的 `evaluateJavascript` 是
  `probeKernel` 的一次性读回，无入站
- **Worker 还不在 page 里**：`web-boot.ts:538` 用 `new Worker(worker-entry.js)` 起成 **dedicated Worker**，
  即使 page 上有 shim 它也够不到，必须经 `WorkerTunnel` 中继——**那是第二层新代码**
- `:dsh` **刻意不依赖** `:engine`（`:dsh/build.gradle.kts:76-84`），所以 `:dsh` 无法自己把 handler 注册进 engine

**所以 `ubuntu.exec/status/fetch` 今天走的是 `0x20 EXEC_REQ`**，和 accelerator 同一条信道，
只是挂在 `phone` 工具目录下。**「不出行」这个说法要撤掉。**

### 为什么不做（判断，不是偷懒）

做成 §12 的 bridge 需要：`:engine` 的 `@JavascriptInterface` 入站 + document-start nonce +
出站 `evaluateJavascript` settle + `WorkerTunnel` 中继 + `:platform` SPI + 解开 `:dsh` 对 `:engine` 的刻意的非依赖。

**收益是什么？** 让「传输方式」这个描述变准确。**`0x20` 和 bridge 都走本机 loopback，都不离开设备**——
所以这不是安全属性，是**机制的名字**。

**用模块级改动去换一句描述准确，不划算。** 正确做法是**把描述改对**（本节就是），
并在 PR 的已知缺口里登记。真正该做 §12 bridge 的时机是：**当有第二个宿主工具也需要它的时候**——
那时它是复用，不是为一个方法新建一条通道。

### 4.3.3 写工具走的是只读 accelerator 的通道（**违反 exec.md §3**）

审计指出：`phone` 在 `ExecCapability.ACCELERATORS` 白名单里（`spec/v1/exec.md:113` 只允许
**只读** accelerator 走 `0x20`），而 `phone ubuntu run` **是写操作**（落 job 记录、跑任意命令）。

**这不是「缺一件东西」，是「破一条不变式」。** 我之前把它写成「传输不是设计表里的『不出行』」，
那个说法把违规说成了缺口。

**短期处置**：登记为 known divergence——「`phone` 目录下的 `ubuntu` 子是写工具，但仍以
`accelerator:phone` 的 `0x20` 出行」。**长期**要么落 §12 的 page↔host bridge，
要么给「宿主工具」拆一条不出现在 accelerator 名录里的传输（后者正是 §4.3.1 说的「等到有第二个」）。

### 4.3.2 两条实现与契约的语义差（登记，未修）

**(1) `ubuntu run` 是「等到终态」，§12.2 要求「立即返回 JobRef」**

`UbuntuHostTool.run` 会 `awaitTerminal`（`UbuntuHostTool.kt:196`），因为宿主工具跑在 `0x20` 的
`EXEC_REQ` 上，那条信道是**请求-响应**形状。而 §12.2 的 `ubuntu.exec` 是「admit 后立即返回 JobRef」，
让调用方轮询 `ubuntu.status`。

**两种都自洽，但 `ubuntu run` 的输出语义不同**：现在它一次调用就把结果给出来，
换成 §12 的形状就要两次。**接线时必须选一个，不能两个都留。**

**(2) 现在接的是 `MockUbuntuAdapter`，不是真 Ubuntu**

宿主是 `MockUbuntuSession`（`backend=mock`，120 ms 后 exit 0，`logTail` 是 `mock ubuntu-24.04: <jobId>`）。

**所以 `ubuntu run -- gcc --version` 今天只证明 transport + JobRef 链路，不证明真的跑了 gcc。**
Agent 也确实看懂了这点并按它行事（见 PR §十七）。**真 gcc 需要真 adapter，不在本轮范围。**

### 4.4 「需要的时候才用」在 Agent 侧怎么表达

三件事，缺一不可：

**1. Agent 必须先知道它存在**

命令的说明要写清它是干什么的、代价是什么。**一个只说「可以跑命令」的说明会让 Agent 拿它当 `bash` 用**——那等于每次都挂载。

说明里必须有的信息：
- 它启动一个**独立的本地 Linux 环境**，为需要完整用户态的任务准备（工具链、包管理器、某个只在 Linux 上跑的程序）
- **它不跑 DSH 的主任务**——回合、上下文、会话状态全部留在 DSH 里
- **启动需要时间、占磁盘、耗电**
- **用完请关掉**（关之前的东西不保留；下次再启动要重新等）
- **日常的 `ls` / `cat` / `git` 不需要它**——那些走现成的 `bash`

**2. Agent 自己决定什么时候用**

这正是需求方说的「需要的时候才用」。**决策权在 Agent，不在宿主**——宿主不能替它判断「这次任务复不复杂」。

**3. 一次批准覆盖本 session，但每个 job 单独可见**

按 §3 第 1 层：**按 session 授权**。Agent 第一次调用时用户批准；本 session 内后续 job 免批。

**这不等于「批准了就看不见了」**：每个 job 仍然**单独密封**、**单独绊线**，`ubuntu.status` 逐 job
报 `internalAccessObserved`。**用户拿到的是逐 job 的可见性，不是逐 job 的批准。**

**仍然要防的一件事**：Agent 不能因为「本 session 已授权」就把它当 `bash` 用。所以 §4.3 第 1 条
（命令说明写清代价）依然必要——**授权是按 session 的，克制是每条命令说明的。**

### 4.5 契约必须写死的四条

1. **`egress`**：本地方案不离机，所以 `egress: false`——**但 `internalAccessObserved` 要单列**，「没离机」和「没被看过」是两件事
2. **「job 成功但摄取失败」**：产物超 288 MB workspace 预算时，状态必须是这个，经 `ubuntu.status` 上浮
3. **密封失败要能上浮**：`chmod` 失败或恢复失败时，**不得开始 job**（fail-closed），并报出来
4. **`ubuntu.status` 必须带 `internalAccessObserved`**

## 5. 同意模型

同意文案必须说清四件事：

1. **这次要用什么**（本地 Ubuntu 运行时 / 一个镜像的哈希）
2. **它能读到什么**：只有工作区下的这些路径（列出）
3. **它读不到什么**：三个内部根在构建期间被密封，**但同 UID 的代码有办法恢复权限**
4. **我们会怎么知道**：访问会被记录，job 结束时告诉你

**判据**：如果用户读完这段文案，对「构建代码能不能看我的会话记录」这个问题的答案仍然是「不知道」，那这段文案就没写好。

**准确的答案应该是**：**「正常情况下看不到；如果它刻意去看了，我们会告诉你。」**

## 5.1 评审指出、初稿漏掉的四个硬点

两份独立评审（GLM / Kimi）各自指出了初稿没算的账。**四条都会改动实现，不是措辞问题。**

### 5.1.1 窗口的真正执法点是**进程树**，不是挂载表

初稿把「用后即弃」当成卸载就完事。**proot 没有 PID namespace**：job 结束 ≠ 进程树结束，后台 fork 出来的进程可以活过「卸载」，继续跑、继续读。

**所以「用后即弃」在初稿里是名义上的。** 要它成立，必须有：

1. **整树收割**：job 结束（含失败/超时/用户取消）时，杀掉**整个进程组**，不是只杀直接子进程
2. **幸存者检测**：收割后用 `/proc` 扫一遍，确认这个 app 的 UID 下没有残留的陌生进程；有就报进 `ubuntu.status`
3. **把窗口的执法点定义成进程组生命周期**——挂载表只是一个视图，不是边界

### 5.1.2 230 MB 进程预算与本地编译天然冲突

`spec/v1/budgets.md` 约束 App 进程内存 ≤ 230 MB。而 **`gcc` + `ld` 随便几百 MB RSS**，guest 作为**子进程**跑在同一个 app 里，内存压力下会被 LMK **连坐整个 app 杀掉**。

这不只是「可能慢」——是**跑一次真实编译就把 DSH 自己搞死**。

**对策（必须写进契约）**：
- `ubuntu.status` 要能报「因内存压力被系统回收」
- 启动 job 前做**可用内存预检**，不够就**拒绝开始**而不是跑一半被杀
- 单 job 的 RSS 上限要显式声明，超出**主动杀**而不是等 LMK

### 5.1.3 `egress` 记账是契约层的类别错误（评审认为这是最大风险）

初稿说「本地方案不离机，所以 `egress: false`」。

**评审指出**：本地同 UID guest **没离机，但离开了 Worker 权威**。现有布尔字段没有真值可写——
写 `false` 等于**审计系统对用户说谎**，而审计在「spec 是唯一法官」的治理下是**证词**，append-only，事后不可追改。

**我的处理**：`egress` 保持它原本的含义（**字节是否离开设备**），本地方案确实是 `false`。
但**必须新增一个字段记录「离开了哪个权威」**：

```
egress: false              // 字节没离开这台设备
authorityExited: "worker-vfs"   // 但它离开了 Worker 的 VFS 权威
```

云端适配器则是 `egress: true, authorityExited: "device"`。

**这两个字段不能合并**——「没离机」和「没离开 Worker 的执法点」是两件事。

**⚠️ 这一条必须先落 spec，才能开始本地形态的任何实现。** 评审把它列为硬条件之一。

### 5.1.4 产物要「按需取」，不能自动物化

初稿说「产物一律走标准 VFS mutation」。**对回写路径成立，对预算不成立**：

- workspace 预算 **288 MB**
- 单 mutation **≤ 15 MiB** + suffix append
- 真实构建产物动辄几十上百 MB

**「协议全在」只说明能写，没说明写得下。** 正确形状：

```
JobRef → 产物清单（名字 + 大小）
       → 按需 fetch（预检 288 MB、单文件 ≤ 15 MiB、超出拒绝并说明）
```

**大产物不该自动落进工作区**——那会把 workspace 撑爆，而用户要的可能只是其中一个文件。

**同理，去程也要算账**：输入快照在 230 MB 约束下必须文件化，走谁的配额要写清。

### 5.1.5 一个工具，N 个环境（命名）

评审指出 `build.run` 把语义锁死在编译，而实际授予是「在外部环境执行任意脚本」——lint / test / codegen 会排队出现，每个开新名字 = **碎片化同意面**。

**已改名 `ubuntu.exec`**，但更准确的是**一个 job 提交工具 + `env` 参数**：

```
ubuntu.exec --env ubuntu-24.04 -- <cmd…>
ubuntu.exec --env gh-actions:ubuntu-latest -- <cmd…>
```

**一个能力面、N 个环境、一套同意与审计。**

## 6. 分阶段

### 阶段 0：契约（spec PR）

`ubuntu.exec` / `ubuntu.status` / JobRef 形状、失败语义、配额语义、`internalAccessObserved`。

**语义上要写清**：这是「把一条命令交给本地 Linux 环境执行并拿回结果」，**不是**「在 Ubuntu 里构建一个产品」。

**验收**：iOS 与 Android 读同一份契约，都能说出「怎么调用、怎么失败」。**按治理规则，特性先落 Swift 基线——本阶段的第一件事是 spec，不是 Android 实现。**

### 阶段 1：密封与绊线（**先做这个，不接 Ubuntu**）

**理由**：这两层是安全对策的**全部**。如果它们不成立，Ubuntu 接进来只是加了一个读得到东西的进程。

- `chmod 000` / 恢复，含「job 中途进程被杀」的恢复测试
- `FileObserver` 绊线
- **用一个 echo 适配器**（一个假 job，`sh -c 'echo hi'`）验证整条链路
- **验收**：
  1. 密封期间，一个测试进程读内部根**失败**
  2. 它 `chmod` 恢复后能读，**绊线记录到了**
  3. 进程被杀后，下次启动权限被修复
  4. 权限恢复失败时，job **不启动**（fail-closed）

### 阶段 2：挂载面（proot + Ubuntu rootfs）

- 挂载表只含工作区
- 环境**用后即弃**（每次 job 从校验过的镜像起新实例）
- **验收**：`find /` 和 `rg --files /` 看不到内部根；**并且**绊线在「刻意 chmod」时报警

### 阶段 3（不做，除非重新评审）

增量、缓存、常驻环境。

## 7. 什么情况下该推翻这份方案

1. **如果 §3 第 3 层的三个前提有一条不成立**（尤其是「DSH 在 job 期间不需要读内部根」），密封层作废，本方案退化成「只挡意外」——那时要重新决定是否接受
2. **如果 `FileObserver` 在实践中漏检严重**（绊线形同虚设），那第 4 层作废，只剩「时间窗 + 挂载表」，需要重新评审
3. **如果真实数据显示热循环工效是硬要求**——本方案不做增量，那就该换方案而不是加状态

### 2026-11-01 契约落地（L47）

阶段 0 的契约文本已写进 `spec/v1/bridge.md` §12（三个方法标 **not implemented**，因为实现、适配器与审计记录都还不存在）。落笔时有六处方案必须修正，**方案原文与契约不一致，以契约为准**：

1. **§4.2 的 `build.status` 是笔误**，契约用 `ubuntu.status`；`build.run` 在 §5.1.5 已经改名，同一段里的旧名字没有跟着改。
2. **「产物不做新 fetch API」不成立。** `ubuntu.status` 只能给清单，字节得单独取；而宿主的 VFS 授权点规定 **只有 Worker 能产生 `VFS_MUT`**（`channel.md` §2/§8：`0x10` 是 worker→host，`mseq` 由 Worker 分配），宿主无法把字节直接写进 workspace。所以契约新增 `ubuntu.fetch`：宿主按块（≤ 512 KiB，正好是 `bridge.md` §4 的二进制上限）把字节交给页面，页面用 `channel.md` §6 已经定死的 mutation 写回（一次 ≤ 15 MiB 的完整写 + suffix append）。**没有新增 HTTP 面**，这保持了 §4.2「不做新 fetch 平面」的本意。
3. **§5.1.4 的「单文件 ≤ 15 MiB」把两个数混在一起。** `budgets.md` §6 明说 15 MiB 只是 **per-mutation 帧上限**，文件上限是分层级的 `single_file_limit`（16–256 MiB）。契约因此写成三个数：单次 mutation ≤ 15 MiB；摄取默认上限 **`fileLimitBytes` = 15 MiB**（一次原子写，不留半个文件），可按环境抬到该层级 `single_file_limit`，**并在 JobRef 里声明**；聚合上限 = workspace 桶 288 MB。抬上限后的回写走 append 链。
4. **`egress` / `authorityExited` 的写入时机。** 契约把两者都定成「事实成立的那一刻写入，此后永不改写」：`egress` 从 `false` 起、只可能在 `handingOff → remote` 变 `true`；`authorityExited` 从 `null` 起、同一时刻取适配器声明的值。**`null` 表示一个字节都没出去**，所以「job 没启动」不需要在 `egress` 上说谎。
5. **`Draining` 与 job 的先后顺序要写死。** 仅说「20 s 内 abort」不够：宿主必须**先**把 job 落成 `reclaiming`，再等适配器；否则 20 s 内的 `ubuntu.status` 会报 `remote`，而宿主已经放弃它——那是审计在说谎。
6. **密封失败与 `admission_closed` 不是一回事。** 前者是「宿主在接活、但拒绝这个 job」，后者是「宿主现在不接活」；契约用同一个 `provider_unavailable` 码 + 不同的 `cause`（`seal_failed` vs `admission_closed` 码），并要求密封失败时 **一次都不许碰适配器**（fail-closed）。

**仍然不做的**：§6 阶段 3（增量、缓存、常驻）。本轮也没有接真 Ubuntu、没接 GitHub：端到端只在 `android/dsh` 的 mock 适配器上跑通。
