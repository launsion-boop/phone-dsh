# iOS ↔ Android side-by-side sheets

> **Read this first (L86, 2026-11-02): the Android half is not the App.**
> These PNGs are rendered by the instrumented harness from *hand-authored*
> `ChatScreenState` / `SessionsScreenState` samples in
> `android/lib/src/androidTest/**`, not by the running product. The real app was
> captured on a device in the same 402×874 pt @3× frame and put next to both
> halves: on the home screen the sample sits **6.27 %** from iOS while the real
> App sat **79–80 %** from *both* (after the L86 home rebuild it sits 10.34 %
> from iOS — see the report); on 定时任务 the sample is 14 % from iOS and the
> real page 92 %; on 设置 the sample is *further* from iOS (47.87 %) than the real
> page (13.70 %). Five registered states that the samples draw
> (`page-sessions-empty/default/many/ungrouped`, `page-sessions-schedules`) are
> unreachable on the real host, because it reports no workspace folders and no
> schedule snapshot.
> **A difference on these sheets is a fact about the samples until a real-device
> capture says otherwise.** See [`real-device/REPORT.md`](real-device/REPORT.md).

One PNG per registered parity state: the **iOS baseline on the left**, the
**Android parity capture on the right**, both resampled by *one* factor and
top-aligned. One sheet is `<state>__ios-left.png`, where `<state>` is the
registry's Android capture name (`page-chat-default`), and the caption on the
sheet names both source files.

Generated by
[`android/tools/ui-parity-sheet.py`](../../../android/tools/ui-parity-sheet.py)
from
[`docs/receipts/ios-baseline-screens/`](../ios-baseline-screens/)
and
[`android/lib/src/test/resources/screenshots/ios-parity/`](../../../android/lib/src/test/resources/screenshots/ios-parity/).
The pair is found through the registry's own join key (`iosFile` →
`androidName`), never by guessing from a file name.

* **能 / can prove:** 同一个注册状态两边各有一张图；两张图是同一个 402 × 874 pt
  @ 3× 的框；同一条水平线上两边画了什么，人眼可以直接看。
  Both sides have a capture of the same registered state, in the same
  402 × 874 pt @ 3× frame, so their vertical positions are directly comparable
  and a human can see, per state, what each side draws at the same height.
* **不能 / cannot prove:** 像素一致，或视觉一致。两边字体栅格不同、系统 chrome
  不同、文案各自本地化；本目录**不做像素 diff**，也不是 parity 证明。
  It does not prove pixel or visual equality. CoreText and Android's
  Minikin/HarfBuzz rasterise glyphs differently, the two systems draw different
  chrome, and the copy is localised on each side. There is **no pixel diff** in
  this directory, and it is not a parity proof.

## Why there is no pixel diff

A raw diff between these two PNGs is dominated by font rasterisation and by
platform chrome, not by layout. It would produce a large number that looks like
evidence and means nothing — the same trap as "54/54 screenshots PASS". The
sheet therefore does **not** compute one, and nothing in this directory claims a
pixel percentage. What it does instead is put the two frames where a human can
look at them, with a ruler so a vertical offset is measured rather than
estimated.

## What one sheet contains

| part | what it is |
|---|---|
| title | state name + frame height Δ (iOS px − Android px) |
| per-side caption | source file + pixel size of that side |
| shared ruler | **frame** pixels of the source (ticks every 100 px, labels every 200) |
| two panels | same scale, top-aligned, iOS left / Android right |
| footer | the shared scale factor and the frame both sides were captured in |

If the two frames ever differ in height, the sheet draws a dashed red line at the
shorter frame's bottom and labels the remaining band `Δ … px`, so a crop is never
silent. Today every registered pair is 1206 × 2622 on both sides, so Δ is 0 px
everywhere — that is itself the receipt that the *frame* contract matches.

## What is deliberately not annotated

**No structural-block boxes.** The capture harness records the frame size and
font metrics only (`metrics.txt` in the baseline directory); it records no layout
tree and no element geometry per state. Marking "a block that exists on one side
and not the other" from ink heuristics would be a guess, and a guessed annotation
is worse than none. The ruler is *frame* geometry, not element geometry. If a
per-state geometry receipt ever exists, the annotation can be added then — with
data, not with a heuristic.

## A systematic difference visible on every sheet

The iOS baseline includes the simulator's status bar (09:41, wifi, battery); the
Android harness hides the system bars. So the iOS panel carries chrome at the top
that the Android panel does not. Compare the content **below** that band, and do
not read an absolute y as a layout bug without subtracting it. The same applies at
the bottom: iOS home-indicator / Android gesture bar.

## What a difference on a sheet means

It means exactly one thing: the two states do not render the same, and a human
has to decide whether that is a bug, a deliberate platform difference, or a
sample that was never faithful. All three have happened in this set. The sheet is
evidence for that review; it is not the verdict.

## What the L43 capture changed

The 2026-11-01 L43 capture flipped five Chat states to `captured` and, in doing
so, re-ran the whole `ios-parity` set. Twenty of the twenty-one existing PNGs came
back **byte-identical**; **`page-settings-runtime.png` changed**, because commit
`8813ca22` (21:37) rewrote `RuntimeDetailsPage` after the previous capture (19:53).
The parity compare on the pre-update tree caught it *before* the update: 302,158
diff px = 9.56 % of the frame, one state of 21. That change is in the baseline
now because the baseline has to describe HEAD, not because this sheet wanted it —
and the sheet is what lets a human see what that 9.56 % actually is.

Provenance of the L43 baselines, because it matters for what the sheets can claim:
the PNGs were captured from an immutable `git archive HEAD` tree plus the two L43
edits, while the shared working tree carried another lane's uncommitted changes.
The in-repo `--profile ios-parity` compare immediately after the copy passed 26/26
against the live tree, so the baselines describe the live render and not only the
archived one.

## Coverage

[`metrics.txt`](metrics.txt) is the index: one row per registered parity state
with the iOS size, the Android size, `Δw` / `Δh`, the sheet's scale, whether a
sheet exists, and **where the Android side came from** (`device` = a Compose
harness capture in the parity baseline directory, `adb` = a hand `adb screencap`).
`paired=no` rows are states with no Android capture at this revision — a visible
gap, not a silent omission.

* **27 of 27** parity states are paired as of the 2026-11-02 L64 pass: 26 from
  the Compose harness plus **`env-home`**, which is an `adb screencap` of the
  launcher and therefore lives in [`adb/env-home.png`](adb/env-home.png) instead
  of the page baseline directory. The registry keeps that row `pending` on
  purpose: a launcher screenshot is an environment proof, not a page, and must
  not be frozen into the page regression baseline. What its sheet can prove is
  the frame (1206 × 2622 px, Δ 0) and which OS surface is on each side; it cannot
  prove that Android's own render drifted, because that capture is not in the
  gate.
* The three `androidOnly` states (`page-device-connection`,
  `page-device-session`, `page-session-artifacts`) have no iOS baseline and are
  out of scope: there is nothing to lay them next to.
* The sheets are built from the Android **self-baseline**. They inherit its
  limit: a wrong-but-stable Android render would sit next to iOS looking
  "stable". Only the human review this directory exists to support can catch
  that.

[`DIFFS.md`](DIFFS.md) is that review, written down: one section per state, every
visible difference as `control / iOS value / Android value / delta` in points
(`pt = px / 3`), plus what was fixed (before → after), what could not be fixed and
why, and the places where the structural gate is green while the pixels disagree.

## Regenerating

```bash
python3 android/tools/ui-parity-sheet.py                 # all paired states
python3 android/tools/ui-parity-sheet.py --state page-chat-permission
python3 android/tools/ui-parity-sheet.py --panel-height 900 --out /tmp/sheets
```

The `adb` capture is refreshed by hand, at the parity frame, on a booted
emulator (the capture tool resets the display when it exits, so set it again):

```bash
adb shell wm size 1206x2622 && adb shell wm density 480
adb shell input keyevent KEYCODE_HOME
adb -s <serial> exec-out screencap -p > docs/receipts/ui-parity-sheet/adb/env-home.png
python3 android/tools/ui-parity-sheet.py --state env-home
```

Needs `sips` (macOS, used for the resample) and Pillow (used for the canvas;
`sips` can resize and pad but cannot concatenate two PNGs). Pillow is already used
by `android/tools/test_screenshot_compare.py` when present. The tool only reads
the baselines; it never writes them.
