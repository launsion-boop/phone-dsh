## 1. Identification and roles

- **Trigger → current → expected.** The user decided (plan v2 §§3–9, 2026-11-09)
  to give the iOS App a PC workspace backed by DSH on the user's PC through a
  public relay, with end-to-end encryption and a paired identity. Today there is
  no PCLink contract: the PC Phase 0 spike used a plaintext relay and plain
  `machineId` strings, the iOS Phase 0 spike used `DSHWebTransport`, and the
  relay authentication, E2E handshake, pairing, frame limits, error codes,
  endpoint retry classes and CLI↔plugin boundary were unspecified. Expected: a
  frozen P28 contract with shared valid/invalid vectors and schemas so B
  (relay), C (PC plugin/CLI) and D (iOS) can implement in parallel without
  redefining a boundary.
- **Coordinator / contract owner:** this change (P28 owner). B relay, C plugin
  and D iOS implementers are assigned separately; the reviewer/integrator must
  not be an implementer of the end under review.
- **Owning contract:** [spec/pclink/v1/README.md](../../spec/pclink/v1/README.md)
  (`pclink-v1.2`), schemas under `spec/pclink/v1/schema/`, golden document
  `spec/pclink/v1/golden/pclink-v1-vectors.json`, schema samples
  `spec/pclink/v1/golden/schema-samples.json`, endpoint inventory
  `spec/pclink/v1/endpoints.json`.
- **Affected producers/consumers:** Node relay (`relay/**`, B); Node PC plugin,
  CLI and shared core (`pclink/plugin/**`, `pclink/cli/**`, `pclink/core/**`, C);
  Swift iOS module and tests (`Sources/PhoneDSHPCLink/**`,
  `Tests/PhoneDSHPCLinkTests/**`, D); the App wiring is the D-stage P09/P27
  change in `examples/probe-app/**`. P14 and P06 are dependencies only.
- **Status:** P28 `target`; every end is `not started` at this freeze. This
  record is the revised `pclink-v1.2` freeze after the second review round; it
  preserves the reviewed `pclink-v1.1` wire bytes except the approved pairing,
  notice and rendezvous changes. Nothing in this change may be called or
  shipped as implemented.

## 3. Compatibility and release

| Producer → consumer | Behaviour |
| --- | --- |
| old → new | No old PCLink producer exists. DSH Remote calls carried by PCLink keep their P14/P06 meaning; a DSH endpoint sees the same `client-request`/stream payload it sees from the browser/local owner. |
| new → old | No old PCLink consumer exists. A future v2 producer is rejected by a v1 receiver with `version_unsupported`; there is no downgrade, alias or second envelope. |
| new → new | This contract, with the shared golden valid and invalid rows and the conformance requirements in §12. The v1.2 pairing/notice/status changes are additive or revised before any implementation; the handshake and AEAD vectors are byte-identical to v1.1. |
| persisted old data → new / rollback | There is no old PCLink persistence. v1.2 `identity.key`/`pairs.json`/`pairs.log`/`admin.json` are read by later v1.2 builds; a changed local identity, a missing/mismatched `pairs.log` line, or a later `unpair` event marks a record unusable and requires re-pair. A v1.1 record is structurally valid (no record field changed), but the v1.2 admin/approval UI adds the pending-peer redaction and notice; there is no record migration. A build without PCLink ignores the directory. Rolling back to a pre-PCLink build removes the feature but not the files; the superseded `pclink-v1` draft's unapproved records are intentionally not adopted. |

- Version rule: new PCLink protocol, not a DSH or P14 version. `pclink-v1.2`
  is the current revised freeze of the same outer `v:1` protocol before
  implementation. `pclink-v1.1` changed transcript/key and pairing bytes;
  `pclink-v1.2` preserves the v1.1 handshake/AEAD bytes and changes only the
  approval ritual, status redaction, admin source-Peer gate/error shape,
  `pclink.notice`, origin-bound rendezvous and the offline hint. Neither MUST
  be mixed with the unfrozen `pclink-v1` draft. `caps` carry `workspace/1` and
  the suite; the DSH tested range is a warning, not a barrier. P14/P06 formats
  are untouched. There is no downgrade path to the draft.
- Release order: A freeze first; B/C/D then proceed in parallel. A relay may be
  deployed before clients; the PC plugin may ship before the iOS module (the
  phone cannot use it without the module); the iOS App may ship with the PC
  backend disabled until the module and plugin are both present. No end may
  claim `implemented` without the §12 runtime evidence.
- Rollback: relay has no persisted state; restarting it loses allowlists,
  rendezvous and quotas. The PC plugin and phone keep their local records; a
  rollback that cannot pair simply shows the feature unavailable, and
  roll-forward can reuse the v1 files if the identity still matches.
- `target` remaining: every PCLink wire message, all schemas/goldens, the relay,
  the plugin/CLI and the Swift module. This freeze is contract-only.

### 4.6 Investigation: `_request` and `assistantStream` on the phone-local path

**Question.** Phase 0 found that through the PC `dsh web` gateway
`session/list {}` is rejected with `missing "_request"` and
`session/follow assistantStream:false` is rejected by boundary validation, while
the phone-local Worker path "seems to tolerate" them (plan v2 §12.2.4). Is the
phone-local path actually more permissive?

**Answer: no. The phone-local path uses the same strict DSH gateway; it does
not have a compatibility shim. The old shapes are invalid there too. The
apparent tolerance is error swallowing at some App call sites, plus the main
chat path using the already-correct `assistantStream:true`.**

Evidence:

- DSH 0.2.2-rc.1 (`plugins/dsh-pin.json` = `66491b05`):
  `packages/api/session-controller/src/index.ts:274,279` declares
  `list(_request: SessionListRequest, signal)`; `SessionListRequest` is
  `types.ts:245`. `packages/api/gateway/src/index.ts:1636-1655`
  (`assertExactArguments`) rejects a missing required wire parameter as
  `gateway/arguments-invalid` (`missing "_request"`).
- `session/follow` declares `assistantStream?: true` at
  `packages/api/session-controller/src/types.ts:493`; the generated strict
  descriptor is `z.literal(true).optional()` at
  `packages/api/session-controller/lib/typert.host.js:354` (JSON Schema
  `const:true`). `gateway/src/index.ts:1698` maps a parse failure to
  `gateway/input-invalid` (`wire field "request" failed boundary validation`).
  Phase 0 observed both errors live on the PC (`pclink-p0-pc` README
  §"Answers to Q1–Q8" and the iOS spike §3): `session/list {}` →
  `gateway/arguments-invalid: missing "_request"`; `assistantStream:false` →
  `wire field "request" failed boundary validation`.

### 4.9 Contract-owner decisions and CCRs

No implementer CCR was received (there are no implementers yet). The
independent security review's minimum fixes were adopted; no direction was
silently changed. The decisions recorded in spec §13 are:

1. A separate plaintext `e2e.handshake` bootstrap carrier is required: the
   first handshake message cannot be AEAD-encrypted before a key exists. It
   carries no identity private key and is bound by signatures/transcripts.
2. Rekey starts at the soft threshold (2^19 frames or 1 GiB) and closes the old
   session immediately after the new `peer.hello`; no 30-second drain. The hard
   cap (2^20 frames or 2 GiB) closes with `session_expired`.
3. No credit and no ack frame in v1; pull-based WebSocket backpressure plus the
   8 MiB value/16 MiB frame caps and cancellation bound memory. "In-flight" is
   the sender's one-at-a-time production rule.
4. The relay is self-contained (Node built-ins + `ws`) and does not import
   `pclink/core`, keeping E2E/pairing-secret code out of the untrusted deployable.
5. QR pairing carries a 128-bit secret and pins `k`; manual pairing uses an
   **80-bit** code (16 Crockford characters, `XXXX-XXXX-XXXX-XXXX`), no SAS,
   and only opens the C slot in explicit `manual` mode. The rendezvous hash is
   bound to the normalized relay origin. The 300 s window makes the ~2^80
   rendezvous/MAC grind infeasible; QR remains recommended.
6. Every pairing (QR and manual) uses compare-the-phone approval before the PC
   sends `pair.confirm`: the phone displays its own `machineId[0:12]`
   (60-bit) fingerprint, the PC shows only the phone name, and the operator
   types the phone-screen value. A mismatch sends `auth_failed` and destroys
   the single-use slot. The CLI requires a TTY and has no `--yes`; the Web UI
   uses DSH browser/owner authentication. PC records carry
   `approvedAt`/`approvedVia`; `pairs.log` is append-only and an unlogged record
   is unusable. The PC sends `pclink.notice` to other established phones after
   success and the Web UI shows a persistent banner. A same-user process, a pty
   TTY bypass or a paired-phone agent with PC shell can still pair; the ritual
   raises cost and the notice/pairs.log detect it. Remote `rpc.*` calls for
   `pclink.admin/` are the PCLink `forbidden` code.
7. Both ends generate a fresh ephemeral X25519 key per handshake, reject
   all-zero/low-order DH, use `salt = th2`, and derive separate
   `k_confirm_phone`/`k_confirm_pc` keys. `T_init` binds the protocol version
   and suite.
8. A PC `session.reject` for `unpaired`/`auth_failed` is signed over `th1` and
   the code. The phone asks the user before deleting a record; an
   unauthenticated reject only fails that handshake, and `auth_failed` never
   auto-deletes or auto-repairs.
9. PC unpair writes a durable `pairs.log` tombstone before removing the record;
   if the tombstone append fails the plugin stays off the relay (fail-closed).
   The PC re-checks the record at `session.confirm`, aborts in-progress
   handshakes on unpair, and closes an idle E2E session after 15 minutes.
10. The admin API verifies exact `Host`, rejects any `Origin`, requires
    `Content-Type: application/json`, and uses an HMAC server-proof challenge
    before the CLI sends the Bearer token. The local admin surface is
    `status/pair/approve/cancel/unpair/rotate-identity`; the Web UI uses the
    owner-only `/api/pclink.admin/*` routes and never sees the token. The
    admin handler refuses a PCLink remote source Peer regardless of the
    endpoint string; the forwarder prefix test is only a fast path. `forbidden`
    is a PCLink code, and `rpc.result.error`/`rpc.stream.error.error` share
    `{code,message,details?}`.
11. While `awaiting_approval`, `status` and the Web UI body expose only the
    verified phone name; the pending machineId/publicKey/fingerprint are
    withheld. The model/fixture and schema sample enforce the redaction.
12. A phone that cannot reach its paired PC for a long time shows the
    manual-unpair hint; after `rotate-identity` the phone cannot learn the new
    identity, so manual removal and re-pairing is the recovery path.

### 4.12 M-B follow-up: DSH dispatch normalization (resolved “待确认”)

**Question.** Does DSH endpoint dispatch do case folding or alias
normalization, which would let a remote PCLink call reach an admin route under
a spelling the forwarder's `pclink.admin/` prefix test misses?

**Conclusion (confirmed against the DSH 0.2.2-rc.1 pin
`/private/tmp/dsh-0.2.2`): no.** Dispatch is exact and case-sensitive:

- `packages/api/gateway/src/index.ts:1269-1273` splits `endpoint` on `/` and
  requires exactly two non-empty segments; the `namespace`/`method` are used
  verbatim.
- `packages/api/gateway/src/index.ts:878-888` resolves the descriptor by exact
  `endpoint` string in the Typert registry; `:891-902` compares
  `binding.namespace` and `(candidate.exportName ?? candidate.method)` with
  exact `!==`/`===`.
- `packages/client/connection/src/rpc-host.ts:361-369` extracts the endpoint
  from the pathname verbatim and validates its shape without lowercasing;
  `:333` requires `message.method === endpoint`.
- `packages/client/connection/src/client/rpc.ts:176-182` validates target
  segments without case normalization.

Therefore the forwarder prefix test sees the same case-sensitive spelling DSH
would dispatch, and no alias can turn a non-`pclink.admin/` endpoint into an
admin method. The handler source-Peer gate is still the authority required by
M-B, because it does not depend on the endpoint string at all.
