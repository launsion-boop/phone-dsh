## 1. Identification and roles

- **Trigger → current → expected.** The user decided (plan v2 §§3–9, 2026-11-09)
  to give the iOS App a PC workspace backed by DSH on the user's PC through a
  public relay, with end-to-end encryption and a paired identity. Today there is
  no PCLink contract: the PC Phase 0 spike used a plaintext relay and plain
  `machineId` strings, the iOS Phase 0 spike used `DSHWebTransport`, and the
  relay authentication, E2E handshake, pairing, frame limits, error codes,
  endpoint retry classes and CLI↔plugin boundary were unspecified. Expected: a
  frozen P28 contract with shared valid/invalid vectors and schemas so B
  (relay), C (PC plugin/CLI) and D (iOS) can implement in parallel without
  redefining a boundary.
- **Coordinator / contract owner:** this change (P28 owner). B relay, C plugin
  and D iOS implementers are assigned separately; the reviewer/integrator must
  not be an implementer of the end under review.
- **Owning contract:** [spec/pclink/v1/README.md](../../spec/pclink/v1/README.md)
  (`pclink-v1.3`), schemas under `spec/pclink/v1/schema/`, golden document
  `spec/pclink/v1/golden/pclink-v1-vectors.json`, schema samples
  `spec/pclink/v1/golden/schema-samples.json`, endpoint inventory
  `spec/pclink/v1/endpoints.json`.
- **Affected producers/consumers:** Node relay (`relay/**`, B); Node PC plugin,
  CLI and shared core (`pclink/plugin/**`, `pclink/cli/**`, `pclink/core/**`, C);
  Swift iOS module and tests (`Sources/PhoneDSHPCLink/**`,
  `Tests/PhoneDSHPCLinkTests/**`, D); the App wiring is the D-stage P09/P27
  change in `examples/probe-app/**`. P14 and P06 are dependencies only.
- **Status:** P28 `target`. B relay is implemented and merged in this branch;
  C reports the §2.3 behaviour implemented in its worktree (not verified in
  this branch); D1b is app wiring only and the decoder change is not started
  here. This record is the revised `pclink-v1.3` freeze after the C implementer
  CCR; it preserves the reviewed handshake/AEAD bytes and changes only the
  wire-JSON acceptance rule and its fixtures. Nothing in this change may be
  called runtime-conformant without the §4.4 evidence.

## 3. Compatibility and release

| Producer → consumer | Behaviour |
| --- | --- |
| old → new | No old PCLink producer exists. DSH Remote calls carried by PCLink keep their P14/P06 meaning; a DSH endpoint sees the same `client-request`/stream payload it sees from the browser/local owner. |
| new → old | No old PCLink consumer exists. A future v2 producer is rejected by a v1 receiver with `version_unsupported`; there is no downgrade, alias or second envelope. |
| new → new | This contract, with the shared golden valid and invalid rows and the conformance requirements in §12. The v1.2 pairing/notice/status changes are additive or revised before any implementation. v1.3 accepts a legal `\u0000` escape in carried DSH values and preserves it; a v1.2 receiver would have rejected that frame, but no v1.2 implementation exists. The handshake and AEAD vectors are byte-identical to v1.1/v1.2. |
| persisted old data → new / rollback | There is no old PCLink persistence. v1.3 `identity.key`/`pairs.json`/`pairs.log`/`admin.json` are read by later v1.3 builds; a changed local identity, a missing/mismatched `pairs.log` line, or a later `unpair` event marks a record unusable and requires re-pair. A v1.1 record is structurally valid (no record field changed), but the v1.2 admin/approval UI adds the pending-peer redaction and notice; there is no record migration. A build without PCLink ignores the directory. Rolling back to a pre-PCLink build removes the feature but not the files; the superseded `pclink-v1` draft's unapproved records are intentionally not adopted. |

- Version rule: new PCLink protocol, not a DSH or P14 version. `pclink-v1.3`
  is the current revised freeze of the same outer `v:1` protocol before
  implementation. `pclink-v1.1` changed transcript/key and pairing bytes;
  `pclink-v1.2` preserved the v1.1 handshake/AEAD bytes and changed the
  approval ritual, status redaction, admin source-Peer gate/error shape,
  `pclink.notice`, origin-bound rendezvous and the offline hint. `pclink-v1.3`
  changes only the §2.3 wire-JSON acceptance rule, the canonical `U+0000`
  vector and the fixtures; it does not change any handshake/AEAD byte. None
  MUST be mixed with the unfrozen `pclink-v1` draft. `caps` carry `workspace/1`
  and the suite; the DSH tested range is a warning, not a barrier. P14/P06
  formats are untouched. There is no downgrade path to the draft.
- Release order: A freeze first; B/C/D then proceed in parallel. A relay may be
  deployed before clients; the PC plugin may ship before the iOS module (the
  phone cannot use it without the module); the iOS App may ship with the PC
  backend disabled until the module and plugin are both present. No end may
  claim `implemented` without the §12 runtime evidence.
- Rollback: relay has no persisted state; restarting it loses allowlists,
  rendezvous and quotas. The PC plugin and phone keep their local records; a
  rollback that cannot pair simply shows the feature unavailable, and
  roll-forward can reuse the v1 files if the identity still matches.
- `target` remaining: P28 is still `target`. B relay is implemented and merged
  in this branch, C reports its implementation in a separate worktree, and D
  (iOS module/decoder and App wiring) still needs the v1.3 decoder behaviour and
  runtime evidence. This change record is contract-only.

## 4. Ownership, acceptance commands and evidence

File ownership is disjoint. Nobody but the contract owner edits `spec/**`,
this change record, or another end's files. A problem with the contract is a
CONTRACT CHANGE REQUEST (AGENTS.md §3.3), not a local workaround.

### 4.1 B — relay (`relay/**`, Node)

Owns `relay/**` only: an independent `package.json` with exactly
`"ws": "8.21.3"` pinned (no lockfile-less `^`), `relay.mjs`/modules, tests and a
container/compose definition. The relay is **self-contained** (contract decision
§13.4): it imports only Node built-ins and `ws`; it must not import
`pclink/core` or any E2E/pairing-secret code. It implements §3 only: relay auth,
routing/allowlist/replacement, pair rendezvous, limits/heartbeats, relay errors,
metadata-only logging and no filesystem writes. It never parses `e2e.body`.

Acceptance (all runnable from the repo root; a missing tool is SKIP/INCOMPLETE):

```sh
cd relay && npm ci && npm test
node spec/pclink/v1/tools/vectors.mjs --check
python3 spec/pclink/v1/tools/check_samples.py --root .
```

`relay` tests must cover: two-user isolation, non-allowlisted `e2e` drop,
`e2e.handshake` bypass only for the four handshake body types, the separate
source/target handshake buckets, replacement/role conflict, `relay.offline`,
per-IP/pair/daily limits with IPv6 /64 aggregation, max two slots per
connection, pairing expiry/single-success/10-join/5-per-IP limits, heartbeat
timeout and phone idle close, and a static/no-fs assertion. The relay must
consume the shared vectors through its real auth/base32/machineId code (not a
copied expected value). It never sees or checks a SAS. **v1.3 impact:** the
relay's outer strict parser may keep rejecting escaped `\u0000` as well as the
literal byte; relay-plane frames and `e2e.handshake` contain only PCLink-owned
fields and no DSH passthrough value, so the §2.3 allowance is not observable
there. The relay remains unchanged; its full test suite is the check.

`/api/pclink.admin/*` routes. It validates every frame locally; it never trusts
the relay. It implements the endpoint table and the §7 retry classification but
does not add an endpoint whitelist.

Acceptance:

### 4.9 Contract-owner decisions and CCRs

One implementer CCR was received after the relay/D1b integration: the C
implementer's NUL/carried-value conflict. It is adopted in full and recorded
verbatim with its impact in §4.14. The independent security review's minimum
fixes remain adopted; no direction was silently changed. The decisions
recorded in spec §13 are:

1. A separate plaintext `e2e.handshake` bootstrap carrier is required: the
   first handshake message cannot be AEAD-encrypted before a key exists. It
   carries no identity private key and is bound by signatures/transcripts.
2. Rekey starts at the soft threshold (2^19 frames or 1 GiB) and closes the old
   session immediately after the new `peer.hello`; no 30-second drain. The hard
   cap (2^20 frames or 2 GiB) closes with `session_expired`.
3. No credit and no ack frame in v1; pull-based WebSocket backpressure plus the
   8 MiB value/16 MiB frame caps and cancellation bound memory. "In-flight" is
   the sender's one-at-a-time production rule.
4. The relay is self-contained (Node built-ins + `ws`) and does not import
   `pclink/core`, keeping E2E/pairing-secret code out of the untrusted deployable.
5. QR pairing carries a 128-bit secret and pins `k`; manual pairing uses an
   **80-bit** code (16 Crockford characters, `XXXX-XXXX-XXXX-XXXX`), no SAS,
   and only opens the C slot in explicit `manual` mode. The rendezvous hash is
   bound to the normalized relay origin. The 300 s window makes the ~2^80
   rendezvous/MAC grind infeasible; QR remains recommended.
6. Every pairing (QR and manual) uses compare-the-phone approval before the PC
   sends `pair.confirm`: the phone displays its own `machineId[0:12]`
   (60-bit) fingerprint, the PC shows only the phone name, and the operator
   types the phone-screen value. A mismatch sends `auth_failed` and destroys
   the single-use slot. The CLI requires a TTY and has no `--yes`; the Web UI
   uses DSH browser/owner authentication. PC records carry
   `approvedAt`/`approvedVia`; `pairs.log` is append-only and an unlogged record
   is unusable. The PC sends `pclink.notice` to other established phones after
   success and the Web UI shows a persistent banner. A same-user process, a pty
   TTY bypass or a paired-phone agent with PC shell can still pair; the ritual
   raises cost and the notice/pairs.log detect it. Remote `rpc.*` calls for
   `pclink.admin/` are the PCLink `forbidden` code.
7. Both ends generate a fresh ephemeral X25519 key per handshake, reject
   all-zero/low-order DH, use `salt = th2`, and derive separate
   `k_confirm_phone`/`k_confirm_pc` keys. `T_init` binds the protocol version
   and suite.
8. A PC `session.reject` for `unpaired`/`auth_failed` is signed over `th1` and
   the code. The phone asks the user before deleting a record; an
   unauthenticated reject only fails that handshake, and `auth_failed` never
   auto-deletes or auto-repairs.
9. PC unpair writes a durable `pairs.log` tombstone before removing the record;
   if the tombstone append fails the plugin stays off the relay (fail-closed).
   The PC re-checks the record at `session.confirm`, aborts in-progress
   handshakes on unpair, and closes an idle E2E session after 15 minutes.
10. The admin API verifies exact `Host`, rejects any `Origin`, requires
    `Content-Type: application/json`, and uses an HMAC server-proof challenge
    before the CLI sends the Bearer token. The local admin surface is
    `status/pair/approve/cancel/unpair/rotate-identity`; the Web UI uses the
    owner-only `/api/pclink.admin/*` routes and never sees the token. The
    admin handler refuses a PCLink remote source Peer regardless of the
    endpoint string; the forwarder prefix test is only a fast path. `forbidden`
    is a PCLink code, and `rpc.result.error`/`rpc.stream.error.error` share
    `{code,message,details?}`.
11. While `awaiting_approval`, `status` and the Web UI body expose only the
    verified phone name; the pending machineId/publicKey/fingerprint are
    withheld. The model/fixture and schema sample enforce the redaction.
12. A phone that cannot reach its paired PC for a long time shows the
    manual-unpair hint; after `rotate-identity` the phone cannot learn the new
    identity, so manual removal and re-pairing is the recovery path.
13. The §2.3 strict JSON rule applies to wire bytes, not to decoded DSH values.
    A literal `0x00`, BOM, duplicate member, lone surrogate and non-object root
    are still rejected; a legal `\u0000` escape in a DSH passthrough value is
    accepted and preserved. PCLink-owned fields keep their own field rules,
    and the relay/`e2e.handshake` outer carriers contain no DSH passthrough
    value, so a relay may keep rejecting every NUL in outer frames. This is the
    adopted C CCR (v1.3); no handshake/AEAD byte changes.

### 4.12 M-B follow-up: DSH dispatch normalization (resolved “待确认”)

  requires exactly two non-empty segments; the `namespace`/`method` are used
  verbatim.

### 4.14 CCR C — NUL vs. carried DSH values (adopted, `pclink-v1.3`)

**CCR (verbatim, received from the C implementer after testing against pinned
DSH 0.2.2-rc.1):**

```text
Contract: P28 @ pclink-v1.2   Clause: spec/pclink/v1/README.md §2.3（关联 §6.1/§6.2）
Problem: “inner message MUST reject ... NUL” 与“DSH 值原样承载”在真实 DSH 上冲突。
  pinned DSH 0.2.2-rc.1 的合法模型/工具输出中出现 JSON 转义 \u0000，PC 在严格解码后拒绝 U+0000 → bad_frame 关闭会话，prompt/approval 无法完成。
Proposal: 规则作用于 wire 文本：拒绝裸 NUL/BOM/重复键，但允许合法 JSON 转义 \u0000 作为 DSH 数据原样通过。
```

**Coordinator ruling: adopted the Proposal in full.** The conflict is real on
the pinned DSH: a model/tool result is a JSON value, and a JSON serializer may
legally spell `U+0000` as the six-character escape `\u0000`. The old §2.3 text
was interpreted as a decoded-value ban, so a conformant strict decoder killed
the session (`bad_frame`) before `session/prompt` or an approval could finish.
The contract now states the boundary explicitly:

- The strict JSON rules are wire rules: a literal `0x00` byte, UTF-8 BOM,
  duplicate member at any depth, lone surrogate, `NaN`/`Infinity`, malformed
  UTF-8, leading/trailing bytes and a non-object root are `bad_frame`.
- A legal JSON escape `\u0000` (lowercase or uppercase hex on the wire) is
  accepted. Its decoded `U+0000` is carried as DSH data and is not a frame
  error. The same applies to `\u0001`–`\u001f` inside a carried value.
- PCLink-owned fields keep their own field rules: `name`/`peerName` reject
  C0/C1/`Cf` including `U+0000`; pattern/enum fields (`machineId`, `role`,
  `code`, `id`, `endpoint`, `at`, `fingerprint`) reject it as a non-match.
  Error/close `message` is PCLink display text, not a DSH passthrough.
- The DSH passthrough set is `rpc.call.args`,
  `rpc.stream.open.payload.args`, `rpc.result.result`,
  `rpc.stream.item.value`, and the JSON value reassembled from
  `rpc.result.chunk.data`/`rpc.stream.chunk.data`. These values are never
  character-filtered, NUL-stripped, re-encoded or NFC-normalized.
- `canonical_json` emits `U+0000` as lowercase `\u0000` (no short form) in keys,
  values and nested objects; a new `canonical_json.nul_escape` vector pins both
  a key and a value plus the SHA-256.
- Relay-plane frames and `e2e.handshake` contain only PCLink-owned fields, not
  DSH passthrough values. A relay may keep rejecting every NUL (literal or
  escaped) in outer JSON; this is conformant because the allowance is not
  observable there.

**Delta / fixtures.** §2.3 was rewritten; §3.1 and §5.1 state the outer-carrier
no-DSH-value boundary; §6/§6.1/§6.2 name the passthrough members; §9.1 and §13
record the field/message distinction. `pclink-v1-vectors.json` gains
`canonical_json.nul_escape` and a `json_boundary` section with 6 accepted rows
(escaped `\u0000` in RPC call/stream-open args, result, stream item and decoded
stream/result chunk data) and 8 rejected rows (literal NUL, BOM, duplicate key, nested
duplicate, lone surrogate, non-object root, `pclink.notice.name` U+0000,
`relay.offline.to` machineId U+0000). `schema-samples.json` gains valid RPC
args/stream-item samples with decoded U+0000 and an invalid notice-name U+0000
sample. `vectors.mjs --check` and `check_samples.py` each independently drive
the new rows; the Python checker also feeds the invalid field sample through
the real schema.

**Impact per end.**

- **B relay:** no code change. Its outer strict parser rejects literal NUL and
  escaped `\u0000`; relay frames and `e2e.handshake` carry no DSH passthrough
  value, so the escaped-NUL allowance is not observable to it. Relayed `e2e`
  bodies are ciphertext/base64url and are never decrypted. The full relay test
  suite must stay green.
- **C PC plugin/CLI:** C reports it implemented: its strict reader already rejects
  literal NUL/BOM/duplicates/lone surrogates/non-object roots and preserves
  escaped `\u0000` in `rpc.call.args`, `rpc.result.result`,
  `rpc.stream.item.value` and decoded chunk data. The hard-coded fixture
  `revision` assertion must change to `pclink-v1.3`. This change record does
  not edit `pclink/**`.
- **D iOS:** the decoder must implement the same boundary: accept and preserve
  escaped `\u0000` in the carried values, reject literal `0x00`/BOM/duplicates/
  lone surrogates/non-object roots, emit `\u0000` in canonical JSON and update
  the fixture `revision` expectation. D1b is App wiring only; this decoder
  change is not verified in this branch.
- **Not changed:** handshake transcripts/signatures, `th1`/`th2`/`th3`,
  HKDF keys, AEAD nonce/AAD/ciphertext, relay-auth bytes, pairing MACs,
  canonical key ordering/escaping for every non-NUL scalar, or any relay frame
  shape. `relay_auth`, `handshake`, `frames`, `chunking`, `pairing`,
  `resources` and the pre-existing `invalid` rows are byte-identical to v1.2.
