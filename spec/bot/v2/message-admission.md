# Bot 用户消息接纳（phoneDSH-owned，iOS）

状态：`target`（本文件冻结语义；实现以真实 Swift 代码与测试为准）。
Owning boundary：P26（Bot runtime 行为）；它**不改变** P27 的 `row`／`user-action` wire 形状、
不新增行种类／字段，也不改变 DSH `session/prompt`、`session/cancel` 的官方语义。

## 1. 产品语义

Bot 是一个持续对话者，不是工单队列。用户在 Bot 界面里**感知不到排队**：

1. **输入与发送始终可用。** Bot 正在跑一个回合、正在等审批、正在跑工具时，输入框和发送按钮
   仍然可用；消息**立即**出现在会话里（本地回显），随后由宿主可靠接收。
2. **不要求用户选择。** 没有「排队／插队／等上一轮」的选项，也没有队列位置、队列数量、
   “下一条”之类的 UI。内部必要的串行调度只存在于宿主，不暴露给用户。
3. **补充与纠正进入当前工作。** 用户在一个已接受的 chat 回合进行中再发消息时，宿主用官方
   DSH `session/prompt` 的 `mode:"steer"` 把它送进**当前**回合；模型在该回合的下一个 step 看到它，
   不需要等这一轮结束，也不另起一个并行回合。
4. **不丢、不重复。** 每条被接受的消息恰好投递一次（DSH 以 `requestId` 去重）；传输替换／重连／
   重建会话后，未完成的投递必须用**同一个 requestId** 重试，不产生重复回合或重复消息。
5. **不无条件取消正在进行的有副作用工作。** steer 不取消当前回合、不取消已发出的工具调用、
   不丢弃等待中的审批；只有用户显式「停止」才取消当前回合。
6. **不伪造理解。** 投递失败或还没被宿主接收时，界面不得显示成“已理解／已完成”；失败要可观察、
   可重试，消息保留在会话里，不得静默消失。

## 2. 接纳与投递规则（宿主）

一条用户消息被 UI 接受后，按以下顺序处理：

| 状态 | 宿主行为 |
| --- | --- |
| 没有活动 chat 回合 | 走正常回合：`session/prompt` 新回合（现有路径不改）。 |
| 活动 chat 回合、`promptAccepted == true`、且该回合未被用户停止、不是 hidden／非 chat | 立即以 `mode:"steer"` 投递到该回合；不新建回合、不改回合 kind。 |
| 活动 chat 回合但 `promptAccepted == false`（回合刚打开、还没被宿主接收） | 进入宿主的**待投递缓冲**，在该回合被接收后按发送顺序以 steer 投递；**不得**因为这一小段窗口就把它变成下一回合。 |
| 活动回合在待投递消息发出前结束／被停止／传输被替换 | 若回合正常结束：待投递消息按顺序开启下一个正常回合（不丢失、不合并且不改变顺序）。若用户显式停止：停止只作用于当前回合；待投递消息保留，按正常回合继续（除非用户同时清空）。若传输被替换：未确认的投递用同一 requestId 重试，已确认的不重发。 |

- **发完再核对（回合收尾窗口）**：steer 的预检查与实际 `session/prompt` 之间隔着 actor 跳转，
  回合可能在这段时间结束。官方 DSH 此时把 `agent.steer` 当成下一回合的起始消息（`next-step`
  + wake）；宿主**不得**把已结束回合的结果当成这条消息的结果返回。宿主在 send 返回后重新核对
  目标回合是否仍是同一个 attempt：若已结束，就按“活动回合在投递前结束”处理，用**同一个
  requestId** 走正常回合；DSH 以 requestId 去重（`hasPromptRequest`），因此不会重复投递。
- **缓冲上限**：宿主持有的待投递用户消息最多 **16** 条；超限必须显式失败（可见错误 + 保留输入），
  不得静默丢弃或合并成一条。
- **顺序**：同一会话的待投递消息按 UI 接受顺序投递；不同会话互不阻塞。
- **回合归属**：steer 只投递给**同一个** Bot 的主 chat 回合；不得 steer 进 hidden、routine、Task、
  verifier、maintainer 回合，也不得 steer 进别的会话。不满足时按“没有活动回合”处理。
- **幂等**：requestId 由消息 nonce 决定；重试、重连、重复点击同一 nonce 只产生一次可观察投递。
  用户重复点击产生的是新 nonce＝新消息，不是重试。
- **可观察性**：每次投递结果（accepted／failed／deferred-then-delivered）必须能从宿主事件或
  现有行的状态看出来；不新增 wire 字段。

## 3. UI 规则（Bot 页面）

- Composer 在回合进行中保持可用；有文本时按钮是「发送」，空文本且回合进行中才是「停止」。
  不显示队列选择、队列位置或“等待上一轮”的提示。可见文案与可及性标签不得出现 `steer`／
  “插队”／“排队”这类实现术语；用户看到的只是「发送」。
- **发送文本不得自动拒绝等待中的审批。** 不能把“用户又发了一条消息”当成对所有待确认审批的
  deny；审批只能由用户显式选择、显式停止或既有超时/撤销路径改变。用户消息里明确说“不要/拒绝”
  时，交给模型按现有工具面处理，不由 Composer 隐式批量拒绝。
- 本地回显立即出现；不得等宿主接受后才显示。
- 「发送中／未接收」是状态行，不是队列；不得出现“第 N 条排队中”。
- 发送失败：消息保留、错误可见、可重试；不得把失败消息从会话里删掉。
- 停止按钮只停止当前回合，不删除已发送的消息，也不假装它们已被处理。

## 4. 验收（真实代码、真实路径）

必须覆盖（测试驱动真实 `BotDSHRemoteRuntime`／dispatcher／`BotChatModel`，不是手写状态）：

1. 回合进行中连续发 2–3 条：全部立即回显；DSH session log 里当前回合收到 steer（`mode` 为 steer
   的 prompt），且没有并行第二个回合。
2. 纠正被当轮消费：第一轮工具/文本进行中发“改成 X”，该回合的下一次模型请求包含它，最终输出按 X。
3. 忙→闲边界：消息恰在回合结束瞬间到达，不丢失；要么被当轮 steer，要么按顺序开下一回合，
   **且返回值必须是这条消息自己那一回合的结果**，不能是上一回合的结果。该窗口必须用可控传输
   在预检查之后、send 返回之前结束回合来复现（真实 `BotDSHRemoteRuntime`，不是手写状态）。
4. 重连／传输替换：待投递消息在替换后仍以同一 requestId 投递一次，不重复、不丢失。
5. 重复点击：同一 nonce 的重试只投递一次；两次独立点击＝两条消息。
6. 停止：只取消当前回合；已显示消息保留；待投递消息不被静默吞掉。
7. 审批／工具不被无故取消：回合进行中再发一条普通文本后，等待中的审批仍然 pending（不被
   Composer 自动 deny），正在跑的工具调用不被取消；只有用户显式点审批或显式停止才改变。
8. 文案：运行中发送的可见文案/可及性标签是「发送」，不含 `steer`／排队／插队术语。
9. 真实消费：纠正消息进入当前回合后，用该回合**后续真实模型请求/工具调用**证明它被消费
   （例如最终产物按纠正后的要求），不能只断言 prompt 的 `mode` 字符串。

不可用以下方式“通过”：关闭 composer、加队列 UI、把 steer 降级成新回合、放宽现有审批/取消断言、
把 mock 当真实模型证据。真机／后台／弱网只有实际运行才记 PASS。
