# LAN device discovery and MCP profile v1

Status: `implemented` for LAN discovery and phone-to-device MCP in the registered Swift and reference Python ends; host runtime evidence is in the change records. The A-label exclusion and name-consistency rules (revision `lan-names-v2`) bind the Swift, Python reference and target-only Android decoders, the Worker MCP input path and the reference device publisher; evidence is in [PC-20261108-lan-names-trust](../../../docs/protocol-changes/PC-20261108-lan-names-trust.md). The per-device certificate pin trust model below is `target`: phones still validate with the OS trust store. An iPhone and physical LAN-device run remains unverified. The separately authorized device-task profile remains `target`. This profile reuses the existing phoneDSH Streamable HTTP MCP client, native MCP grant store and MCP tool catalog. It does not redefine MCP JSON-RPC, add an envelope, or alter the existing host device receipt schema.

## Discovery

A device advertises DNS-SD service `_pdsh-mcp._tcp` in the local domain. Its SRV record carries its DNS hostname and listening TCP port. The TXT record MUST contain `profile=pdsh-mcp-1` (UTF-8, case sensitive); other TXT keys are ignored. No token, tool descriptions, personal data or stable device secret is advertised. The device serves Streamable HTTP MCP at the fixed path `/mcp` over HTTPS at the advertised hostname and port. TXT data is a sequence of DNS-SD length-prefixed byte strings (each at most 255 bytes); parse the raw data before any dictionary conversion. A `profile` key without `=`, a repeated `profile` key, malformed length framing, a missing key, invalid UTF-8 profile value, invalid hostname or port, and other profile values are rejected. TXT keys are compared case-insensitively; the value is case sensitive. Service instance name is display-only and must be 1–63 UTF-8 bytes. DNS-SD responses, names, addresses, and TXT data are untrusted and not an authorization or identity assertion. Discovery never connects, adds a grant, or calls a tool. Discovery must be explicitly started by the user; removal and timeouts remove or expire candidates. Users may add an MCP server manually when multicast cannot reach a device.

The phone derives the canonical hostname `H` from the SRV target with the algorithm in [Hostname canonical form](#hostname-canonical-form), uses `/mcp`, and omits the port only when it is 443. It presents this HTTPS URL with `H`, not the service name or a selected IP address. A candidate becomes a configured MCP server only after explicit user selection, entry of its device credential, and saving the existing exact-URL grant. `H` is also the TLS server name and certificate verification name ([Name consistency](#name-consistency)). Until the [production trust model](#tls-trust-model) is implemented, `H` must validate against the device's TLS certificate with the OS trust store; no invalid-certificate fallback or silent downgrade is allowed. A DNS-SD record, IP address, bearer token alone, or device display name cannot establish device identity.

## Authorization and tools

The device requires a per-device bearer credential provisioned to the user via a separate authenticated out-of-band channel. The phone stores it as the existing host-managed `Authorization` MCP header; it is never stored in the Worker registry, TXT records, model context or logs. The device checks authentication before exposing MCP initialization, tool listing or calls. Reject missing or invalid credentials; do not redirect requests containing credentials. Credential generation, provisioning, revocation and certificate lifecycle are device administration functions, not mDNS functions. Device hostname, credential and exact URL grant must be reconfirmed if the endpoint changes.

Once authorized, the existing MCP initialize and `tools/list` exchange supplies each device's tools, descriptions and `inputSchema`; the existing Worker exposes them under its server namespace. Device-provided text and schemas are untrusted data. The user grants the server URL and credentials; existing phoneDSH tool permissions continue to gate calls. Tool removal/list changes and reconnection follow the existing MCP client behavior. The device returns truthful execution results; a transport timeout, cancellation or disconnect does not prove that an operation failed or was undone. A client MUST NOT blindly replay a side-effecting call. A device that offers a side-effecting skill must document its request identity, deduplication window and query/recovery behavior; absent those guarantees the outcome after lost response is unknown. MCP JSON-RPC IDs correlate responses and are not a durable idempotency key. P07 `DeviceReceipt` is produced only when the device confirms its outcome; unknown transport state is not a receipt.

## Interoperability and bounds

MCP protocol versions are negotiated by the existing client and server during initialize; incompatible versions fail explicitly. This profile uses the fixed service type and `profile` marker as its discovery major version. Unknown TXT keys are ignored; the marker is mandatory and exact. SRV ports are 1–65535. SRV targets are validated with [Hostname canonical form](#hostname-canonical-form) even when DNS-SD reports the text as a domain name. IPv6 and IPv4 literals are never valid targets. TLS certificate validation uses `H`, not a resolved IP address. A manually configured ordinary MCP server need not advertise this discovery profile and is not subject to these hostname rules.

The shared `golden/lan-discovery.jsonl` vectors exercise candidate decoding, invalid profile, hostname, port and TXT, and the generated URL; both the phone decoder and reference device advertisement generator consume them. The ordered raw TXT bytes in `golden/lan-discovery-raw.jsonl` (shape in `schema/lan-discovery-raw-vector.schema.json`) additionally exercise malformed framing, binary unknown entries and case-insensitive duplicate profile keys; the Swift, Python and Android candidate decoders must consume these vectors. `golden/lan-discovery-alabel.jsonl` (same raw shape) holds the A-label and U-label cases of rule 4; `golden/lan-publication.jsonl` (shape in `schema/lan-publication-vector.schema.json`) holds the name-consistency cases. Every candidate decoder consumes both files; the Worker MCP input path consumes every accepted URL of `lan-discovery.jsonl`, `lan-discovery-raw.jsonl`, `lan-discovery-alabel.jsonl` and the `consistent` rows of `lan-publication.jsonl`. Each vector has exactly one expected `url` or `error`. Android is a partial implementation until its actual DNS-SD provider supplies the raw TXT bytes and SRV hostname without lossy conversion and the existing MCP authorization flow is wired and verified. The profile itself makes no promise that multicast works across VLANs, that a device is continuously online, that a connected device's tools are safe, or that a disconnected command can be replayed.

## Hostname canonical form

Revision `lan-names-v2`. Every end computes `H = canon(t)` from an SRV target, and a reference device computes it from its configured hostname, with exactly these ordered steps; any failure rejects the whole advertisement as `invalid_advertisement`:

1. `t` is at most 254 bytes and every byte is ASCII (below 0x80). This is checked on the original text before any case mapping, so U-labels, fullwidth letters, non-ASCII full stops (U+3002 and similar) and characters that case-fold to ASCII (the Kelvin sign) are rejected rather than mapped.
2. Remove at most one final root `.`, then lowercase ASCII `A`–`Z` only. No Unicode normalization, IDNA mapping or Punycode decoding is performed.
3. The result is 1–253 bytes; each `.`-separated label is 1–63 bytes of `a`–`z`, `0`–`9` and `-`, and does not begin or end with `-`.
4. **No label begins with `xn--`** (the A-label prefix, checked after step 2 so `XN--` is included). Such labels are rejected whether or not their Punycode is valid. Other labels with hyphens in positions 3–4 (for example `ab--cd`) remain valid LDH labels.
5. The final label is neither one or more decimal digits nor `0x` followed by zero or more hexadecimal digits, regardless of numerical range, number of labels or leading zeroes (URL and resolver stacks can read these as IPv4 literals in dotted, shortened, octal or hexadecimal form). A nonnumeric final label such as `123.example` or `0x.example` remains eligible.

Rationale for rule 4 (GAP-18): for an ASCII host with no label beginning `xn--`, the WHATWG URL host parser's domain-to-ASCII step is defined to be ASCII lowercasing, independent of the runtime's Unicode or UTS #46 data, and rule 5 excludes exactly the hosts its "ends in a number" step would treat as IPv4. Any accepted `H` therefore parses unchanged in the Worker URL parser (Node and WebKit alike), in Foundation `URLComponents`, in Python and in Kotlin, and TLS libraries compare it byte for byte. With `xn--` labels, Node 22/ICU 77, Node 24/ICU 78, WebKit and Python IDNA2008 were observed to disagree on validity ([CCR](../../../docs/protocol-changes/PC-20261107-lan-idna-ccr.md)); no shared pinned IDNA implementation exists on the four ends. Internationalized device names are therefore outside discovery profile `pdsh-mcp-1`: such a device advertises an LDH name, or the user configures it manually as an ordinary MCP server. Admitting A-labels later requires a new profile revision with a shared, versioned validator and actual Worker-runtime evidence; it must not be added by one end.

## Name consistency

One value, `H`, names the device at every layer (GAP-17). For an accepted advertisement and the resulting connection all of the following are byte-identical:

| Layer | Value |
| --- | --- |
| Advertised SRV target | `canon(target) = H` (the target may carry one root dot or upper case) |
| MCP URL host | `H` (`https://H[:port]/mcp`) |
| HTTP `Host` authority | `H`, or `H:port` when the port is not 443 |
| TLS SNI `server_name` | `H` (no trailing dot) |
| Certificate verification name | `H`, matched against a `subjectAltName` dNSName |

Phone ends never substitute the service instance name, a resolved address, a reverse-resolved name or a user-edited host for `H`, and never override the HTTP stack's SNI or verification name. Changing the device hostname or port is an endpoint change: the URL grant, credential and (once implemented) pin are reconfirmed.

A conforming device must, before advertising and for as long as it advertises:

- configure `H` such that `canon(H)` succeeds, and serve TLS only with a certificate that carries `H` as a `subjectAltName` dNSName, compared ASCII case-insensitively without a root dot; wildcard dNSNames and the subject common name do not satisfy this check;
- reject a TLS handshake whose SNI is absent or differs from `H` (`unrecognized_name` alert) and, as before, an HTTP request whose `Host` authority differs;
- advertise SRV target `H` (or `H.`) and its listening port. When the platform publisher chooses the target (for example the system Bonjour hostname), the device must not assume it equals `H`.
- verify the record that was actually published within a bounded time: the platform DNS-SD service registered the requested instance name without renaming it, and resolving that instance through the platform resolver yields only targets with `canon(target) = H`, only the listening port, and the `profile=pdsh-mcp-1` TXT entry. Missing, timed-out, renamed or mismatching publication withdraws the advertisement and is reported as a failure; the device does not keep advertising inconsistent values.

The static checks are expressed by `golden/lan-publication.jsonl`. Each row gives the configured `hostname`, the certificate's `certificate_dns_names`, the published `srv_target`/`srv_port` and the listening `port`. `url` is the candidate URL a phone decoder must build from the published SRV values (absent when it must reject them); `result` is `consistent` or the first failing check in this order: `hostname_invalid` (configured name fails `canon`), `certificate_name_missing`, `srv_target_invalid` (a phone decoder rejects the published SRV target or port), `srv_target_mismatch`, `srv_port_mismatch`. Runtime-only failures (registration rename, resolution timeout, publisher exit) are reported as `publication_unverified`. These names are reference diagnostics, not a wire field. Phone ends assert their decoder output equals `url` and, for `consistent` rows, that its host equals `canon(hostname)`; the reference device asserts `result`; the Worker path asserts `consistent` URLs keep their host.

## TLS trust model

Decision (`target`, not yet implemented on any phone end): **a discovered device is trusted through a per-device public-key pin enrolled out of band together with its bearer credential.** Current phones use the OS trust store ([Discovery](#discovery)); that remains the behavior until a phone end implements and verifies this section.

Options considered:

| Option | Assessment |
| --- | --- |
| Publicly trusted certificate for `H` via the system trust store | Public CAs do not issue for `.local` or other non-public names; a public name needs domain ownership, Internet ACME/DNS-01 access and split-horizon DNS, and publishes device names in Certificate Transparency logs. Unsuitable as the default for LAN devices. A device that has one may still be added as an ordinary manually configured MCP server. |
| User-installed local CA | On iOS and Android a user-trusted root applies to all TLS on the phone (Safari, every app), typically without name constraints, so the holder of one device administration key can intercept unrelated traffic; installation is a security-sensitive profile flow and revocation is manual. Least-privilege is violated. Not chosen; enterprise-managed deployments may continue to use OS trust for manually configured servers. |
| Per-device pin enrolled with the credential | Binds TLS identity to the same authenticated out-of-band enrollment that already supplies the bearer credential; trust is scoped to one exact URL grant; no global trust change; works offline and for `.local`. **Chosen.** |

Normative target behavior:

1. **Pin format.** `sha256/` followed by the standard padded Base64 (RFC 4648 §4, 44 characters) of the SHA-256 digest of the leaf certificate's DER `SubjectPublicKeyInfo` (the RFC 7469 `pin-sha256` value). A grant holds one or two pins (current, and next during rotation); other lengths, encodings or algorithms are rejected at enrollment.
2. **Enrollment.** The device administrator delivers `H`, port, bearer credential and pin set as one bundle through the separate authenticated out-of-band channel already required for the credential (for example the device's own display or management portal). Pins never come from DNS-SD, TXT, the TLS handshake (no trust-on-first-use) or the Worker, and the phone offers no "trust this certificate" prompt. Enrollment saves URL grant, credential and pins atomically in the native host-managed secret store; the Worker registry never holds pins or credentials.
3. **Connection check.** For every TLS connection to an enrolled grant (Worker MCP egress and the device task inbox alike) the native layer sends SNI `H` and accepts the server only if: the leaf `SubjectPublicKeyInfo` digest is in the pin set; the leaf carries dNSName `H` (wildcards and common name not accepted); the leaf validity period contains the phone's current time; and, when an extended key usage extension is present, it permits server authentication. A chain to a system root is neither required nor sufficient: a publicly trusted certificate with an unenrolled key fails. TLS 1.2 is the minimum. The bearer credential is sent only after this check succeeds.
4. **Rotation.** Because the pin covers the key, not the certificate, a device may renew its certificate with the same key without phone changes. To change keys the administrator re-enrolls with the pin set `{current, next}`, the device switches keys, and a later enrollment removes the old pin. A grant never holds more than two pins.
5. **Forget and revocation.** Forgetting the device removes URL grant, credential and pins together; there is no partial state that keeps a pin without its grant or the reverse. Device-side credential revocation is unchanged. There is no CRL/OCSP: a compromised device key is handled by forgetting the device and re-enrolling a new key. Removing pins from a grant, or switching it to OS trust, requires the same out-of-band re-enrollment and cannot be requested by the Worker or by discovery data.
6. **Failure.** A pin, name, validity or SNI failure fails the connection closed with a non-secret diagnostic (`tls_pin_mismatch`, `tls_name_mismatch`, `tls_certificate_expired`). It does not fall back to OS trust, another address, plain HTTP or a different hostname, does not prompt the user to accept the certificate, and does not send the credential. A tool call whose connection fails before the request is sent was not delivered; an established request that then loses its connection keeps the existing unknown-outcome rule.
7. **Compatibility.** Grants without pins (all existing grants) keep OS-trust validation. Old phones ignore pins and continue to require OS trust, so a device with only a self-signed certificate is reachable only by phones implementing this section. Rollback of a phone deletes no grants; a rolled-back phone with pin-only grants fails TLS closed rather than trusting the device.

Implementer acceptance for this section (required before its status changes from `target`): a frozen enrollment bundle format with valid and invalid shared vectors (pin encodings, set sizes, mismatched `H`) under `spec/device/v1`; the P18 grant store change with an old-grant migration and rollback decision; a pin-enforcing trust evaluation shared by the Worker MCP native egress (P05 gateway) and the device task inbox, never by the Worker; enrollment and forget UI; Swift tests with generated certificates covering match, mismatch, wildcard-only, expired, missing SAN, two-pin rotation, forget and no credential sent on failure; equivalent Android tests through a custom `X509TrustManager` (OkHttp `CertificatePinner` alone also requires system trust); the reference device printing its pin; and physical iPhone evidence. Until then no end may implement a partial pin path, a test-only pin in production code, or an "accept self-signed" option.
