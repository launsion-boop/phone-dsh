# LAN device discovery and MCP profile v1

Status: `implemented` for LAN discovery and phone-to-device MCP in the registered Swift and reference Python ends; host runtime evidence is in the change record. An iPhone and physical LAN-device run remains unverified. The separately authorized device-task profile remains `target`. This profile reuses the existing phoneDSH Streamable HTTP MCP client, native MCP grant store and MCP tool catalog. It does not redefine MCP JSON-RPC, add an envelope, or alter the existing host device receipt schema.

## Discovery

A device advertises DNS-SD service `_pdsh-mcp._tcp` in the local domain. Its SRV record carries its DNS hostname and listening TCP port. The TXT record MUST contain `profile=pdsh-mcp-1` (UTF-8, case sensitive); other TXT keys are ignored. No token, tool descriptions, personal data or stable device secret is advertised. The device serves Streamable HTTP MCP at the fixed path `/mcp` over HTTPS at the advertised hostname and port. TXT data is a sequence of DNS-SD length-prefixed byte strings (each at most 255 bytes); parse the raw data before any dictionary conversion. A `profile` key without `=`, a repeated `profile` key, malformed length framing, a missing key, invalid UTF-8 profile value, invalid hostname or port, and other profile values are rejected. TXT keys are compared case-insensitively; the value is case sensitive. Service instance name is display-only and must be 1–63 UTF-8 bytes. DNS-SD responses, names, addresses, and TXT data are untrusted and not an authorization or identity assertion. Discovery never connects, adds a grant, or calls a tool. Discovery must be explicitly started by the user; removal and timeouts remove or expire candidates. Users may add an MCP server manually when multicast cannot reach a device.

The phone lowercases the resolved DNS hostname, removes at most one final DNS root dot, uses `/mcp`, and omits the port only when it is 443. It presents this HTTPS URL with the resolved DNS hostname, not the service name or a selected IP address. A candidate becomes a configured MCP server only after explicit user selection, entry of its device credential, and saving the existing exact-URL grant. The same hostname must validate against the device's TLS certificate with the OS trust store; no invalid-certificate fallback or silent downgrade is allowed. Deployments with a private CA must install and trust it on the phone through their normal provisioning process. A DNS-SD record, IP address, bearer token alone, or device display name cannot establish device identity.

## Authorization and tools

The device requires a per-device bearer credential provisioned to the user via a separate authenticated out-of-band channel. The phone stores it as the existing host-managed `Authorization` MCP header; it is never stored in the Worker registry, TXT records, model context or logs. The device checks authentication before exposing MCP initialization, tool listing or calls. Reject missing or invalid credentials; do not redirect requests containing credentials. Credential generation, provisioning, revocation and certificate lifecycle are device administration functions, not mDNS functions. Device hostname, credential and exact URL grant must be reconfirmed if the endpoint changes.

Once authorized, the existing MCP initialize and `tools/list` exchange supplies each device's tools, descriptions and `inputSchema`; the existing Worker exposes them under its server namespace. Device-provided text and schemas are untrusted data. The user grants the server URL and credentials; existing phoneDSH tool permissions continue to gate calls. Tool removal/list changes and reconnection follow the existing MCP client behavior. The device returns truthful execution results; a transport timeout, cancellation or disconnect does not prove that an operation failed or was undone. A client MUST NOT blindly replay a side-effecting call. A device that offers a side-effecting skill must document its request identity, deduplication window and query/recovery behavior; absent those guarantees the outcome after lost response is unknown. MCP JSON-RPC IDs correlate responses and are not a durable idempotency key. P07 `DeviceReceipt` is produced only when the device confirms its outcome; unknown transport state is not a receipt.

## Interoperability and bounds

MCP protocol versions are negotiated by the existing client and server during initialize; incompatible versions fail explicitly. This profile uses the fixed service type and `profile` marker as its discovery major version. Unknown TXT keys are ignored; the marker is mandatory and exact. SRV ports are 1–65535. Hostnames must be syntactically valid DNS names of at most 253 ASCII bytes with labels of 1–63 bytes. A target ending in a numeric label is not an acceptable discovery hostname: after lowercasing and removing at most one final root dot, reject it when the final label is either one or more decimal digits or `0x` followed by zero or more hexadecimal digits. Reject these forms regardless of numerical range, number of labels, or leading zeroes: URL and resolver implementations can interpret them as IPv4 literals in dotted, shortened, octal or hexadecimal form. A name with a nonnumeric final label, such as `123.example` or `0x.example`, remains eligible. The final-label rule also avoids names that the existing Worker URL parser rejects as malformed numeric hosts. This validation applies to SRV targets even when DNS-SD reports the text as a domain name. IPv6 literals remain invalid under the DNS label syntax. TLS certificate validation uses the advertised DNS hostname, not a resolved IP address. A manually configured ordinary MCP server need not advertise this discovery profile.

The shared `golden/lan-discovery.jsonl` vectors exercise candidate decoding, invalid profile, hostname, port and TXT, and the generated URL; both the phone decoder and reference device advertisement generator consume them. The ordered raw TXT bytes in `golden/lan-discovery-raw.jsonl` (shape in `schema/lan-discovery-raw-vector.schema.json`) additionally exercise malformed framing, binary unknown entries and case-insensitive duplicate profile keys; the Swift and Android candidate decoders must both consume these vectors. Each vector has exactly one expected `url` or `error`. Android is a partial implementation: its bounded mDNS querier supplies the raw TXT bytes and SRV hostname to the shared decoder without lossy conversion ([PC-20261108-android-lan-mdns](../../../docs/protocol-changes/PC-20261108-android-lan-mdns.md)), but the existing MCP authorization flow is not wired on Android (a selected candidate only pre-fills an editor that cannot persist) and discovery has not been verified on a physical phone's Wi-Fi. The profile itself makes no promise that multicast works across VLANs, that a device is continuously online, that a connected device's tools are safe, or that a disconnected command can be replayed.
