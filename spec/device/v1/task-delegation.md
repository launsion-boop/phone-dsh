# Device-initiated DSH tasks, v1

Status: `target`. This contract coordinates the device inbox, the phone's durable task executor, and DSH. It uses the existing P07 DeviceEnvelope and the host harness; it does not define a replacement envelope. BLE and LAN devices submit goals to their own local inbox; the phone initiates the connection and consumes that inbox after explicit user authorization.

## Trust and routing

The user explicitly enables device-originated DSH tasks for each authenticated connection. The default is disabled. Disconnect or revocation stops intake. LAN authorization explicitly covers the derived HTTPS `/tasks` path as well as the existing `/mcp` endpoint; credentials never enter the Worker, model, broadcast, or logs. The LAN host and port must be the same as the selected MCP endpoint, normal TLS hostname verification is mandatory, redirects are rejected, and a changed endpoint or credential revokes the task grant. BLE intake requires the existing encrypted, bonded and negotiated Link connection and its validated device identity. Device names and `requester` are untrusted labels, never authentication.

A task's authenticated `device_id` comes from the connection, never from task text. The phone maps it to its device session. For a device/idempotency-key pair, `msg_id` is lowercase SHA-256 of UTF-8 device ID, a zero byte, then UTF-8 idempotency key. It is used in a P07 uplink envelope with `origin=device`, `dir=up`, `kind=text`, a host-assigned persistent monotonically increasing per-device sequence, the mapped session ID, and the goal text. The harness request ID is exactly `dev:` plus that `msg_id`. The host records this mapping durably; device text is never promoted to system instructions. Session and source attribution must be retained independently of message text.

A device-origin session starts with no model-callable tools: the Worker must create it with a dedicated scoped preset that hides all global tools and denies all tool execution, including future registrations and scoped tools. A missing, changed or unverified isolation preset fails closed before prompting. This profile does not grant phone or device control tools to the task; adding per-device tool grants requires a later contract revision. A static system-level policy may identify the session as device-originated. Tool results, permission requests and question requests are never sent to the device. Only the final assistant text or an explicit terminal failure is returned. No background availability is promised while iOS suspends the app.

## Task and result

The device sends a JSON task with `id`, `idempotency_key`, `requester`, `created_at`, optional `deadline`, and `body={"type":"goal","text":...}`. `id` and `idempotency_key` are 1–64 ASCII characters from `[A-Za-z0-9._:-]`; text is 1–768 UTF-8 bytes and may contain printable characters, newline, carriage return or tab only. `requester` is a display label of 1–128 UTF-8 bytes. Times are RFC 3339 UTC timestamps; if supplied, `deadline` must be later than `created_at`. The phone enforces the earlier of the declared deadline and five minutes after durable acceptance. Devices lacking a real-time clock omit `deadline`; their `created_at` is informational. Unknown task members are ignored, but unknown body types are rejected as unsupported. No binary/media or arbitrary instructions fields are accepted as authority.

Before acknowledging acceptance or sending a prompt, the phone atomically persists the authenticated device identity, task ID, key, content fingerprint, request ID, session ID, deadline and state. The same device/key and same task is deduplicated; a conflicting body or task ID is rejected. A key on another device is a distinct task. At most one task per device is running, with a bounded store of 4096 records; full storage rejects new work instead of forgetting deduplication evidence. A terminal result is persisted before reporting and retried to the device until acknowledged. The device must treat an identical terminal report as idempotent and reject a conflicting report.

An accepted request is not an executed task. While running, loss of connection does not start a second DSH turn. On phone restart, any accepted or running task whose outcome is not provably recorded is reported as `unknown_outcome`, not replayed; no cancellation, timeout or dropped connection proves that an action did not happen. If a task expires before prompt submission it is `expired`; after submission an unconfirmed timeout is `unknown_outcome`. The phone may cancel a timed-out session, but still reports `unknown_outcome` unless a definitive outcome is obtained. Completion reports only final assistant text, capped at 1024 UTF-8 bytes without breaking UTF-8; truncation is explicit. Failure kinds are `denied`, `unavailable`, `expired`, `failed`, `unknown_outcome`. Permission or question requests are not forwarded to the device; they fail closed if the task cannot proceed under the isolated preset.

## LAN binding

The authorized phone opens HTTPS `GET /tasks` on the same origin as `/mcp` with the existing host-managed device bearer credential. The server rejects unauthenticated connections before returning data. It returns `text/event-stream`; each `event: task` contains one JSON task, and it redelivers every unfinished task on reconnect. A heartbeat comment at least every 30 seconds is recommended. The phone limits an SSE line to 8192 bytes, an event to 4096 bytes and unacknowledged in-memory tasks per device to one; malformed or oversized events close the stream. It sends `POST /tasks/<id>/accept`, `.../complete` and `.../fail` with JSON bodies, only after the relevant journal state is durable. Complete carries `{"output":"...","truncated":false}`; fail carries `{"failure":{"kind":"...","message":"..."}}`. The ID path segment uses URL encoding, no query, and no redirects. A duplicate matching terminal result is acknowledged with 200/204 or 409; a conflicting result must not overwrite the original. The existing relay task inbox protocol is the input to this binding; this in-repository revision is the authority for phoneDSH.

## BLE binding

A Link device with both existing Tools v1 negotiation and the listed task tools may expose `pdsh.task.next`, `pdsh.task.accept`, `pdsh.task.complete`, `pdsh.task.fail` through its existing `tools/list`. No new BLE opcode or envelope is used. `next` takes `{}` and returns `{ "task": <task or null> }` in the normal Link completed result. `accept` takes `{ "id": "..." }`; `complete` and `fail` take the same bodies as LAN plus `id`. The device persists its task until a terminal report, supports repeated reads and deduplicates repeated reports. The phone polls only while connected and authorized; Link events are hints and carry no delivery guarantee. The full encoded Link logical request/result, not just text, must fit its existing 4096-byte limit. Devices without all four tools are unsupported for task submission and never receive them. Reserved task tools are host control-plane operations and must not be offered as ordinary model-callable device skills.

## Compatibility and evidence

Older devices omit task tools or return 404 for `/tasks`; the phone leaves task intake unavailable without changing their existing tools. Older phones ignore new device tools and retain ordinary MCP/Link behavior; devices must not infer task acceptance without an explicit accept response. New peers use the same task representation and terminal semantics over their negotiated binding. Existing P07 envelope/receipt schema and old persisted data remain readable; new task journals are additive. Rollback must keep the journal, and cannot re-execute or abandon an unresolved operation as if it failed.

`schema/task.schema.json` defines the shared task shape; semantic UTF-8, timestamp, identity and state-machine rules above are normative. `golden/task-cases.jsonl` contains valid and invalid producer inputs. Both device and phone implementations must consume the same fixtures, and tests must cover unauthorized devices, duplicate/conflicting deliveries, persistence before accept, cancellation, crash after submission, duplicate completion, timeout, reconnect and isolation of device-originated model tools. Static schema checks alone are not runtime conformance.
