# BotFish numeric trajectory and asset contract

```yaml
contract: P09/P26 BotFish renderer (phone-owned, Android-port B8)
status: partial            # iOS app implements; Android is target
contract_revision: e477497b / fish-trajectory-1
owner: P09 (UI projection) + P26 (Bot surface); delegate lane C5
upstream_pin: launsion-boop/dsh-bot bf4075b0a2e8092b04b726c59a7b085d5a37e6f6
last_verified: 2026-11-12 (iOS Simulator 26.2 arm64; Swift 6.2.3)
```

**Status: partial.** The iOS app is the reference implementation and the
trajectory golden below is generated by compiling its real fish sources. The
Android renderer is not implemented; it is the `target` consumer of this
contract and must reproduce the numbers before the P09/P26 row can become
`implemented` (`spec/README.md` §2, §3.1). No claim of Android runtime
conformance is made here.

This file is the owning contract for the numbers a second BotFish renderer must
match. It deliberately does **not** freeze pixels: `paint.js` → Core Graphics and
Canvas draw different antialiasing, curves and colour management. It freezes
the model, the controller, the expression-cell/tint/layer choices and the pose
quantisation, which are pure functions of the inputs and are reproducible by
Kotlin `Double` arithmetic.

The machine-readable fixtures are:

* `spec/ui/v1/bot/fish/golden/trajectory.json` — the frozen trajectory
  (97 cases, 954 sampled frames, generated from the real Swift model);
* `spec/ui/v1/bot/fish/golden/assets.json` — the 35-file asset manifest
  (33 PNGs + 2 atlases), SHA-256, PNG headers, layer map and atlas
  reconciliation;
* `spec/ui/v1/bot/fish/schema/fish-trajectory.schema.json` — the trajectory shape;
* `spec/ui/v1/bot/fish/tools/check_fish.py` — the standalone checker;
* `spec/ui/v1/bot/fish/tools/generate_trajectory.py` — the only supported
  generator, and its `--check` mode.

## 1. Authority, scope and what is normative

Authority order for this file: the current Swift code and the generated goldens
win over this prose. Where this prose and a golden disagree, the golden is the
frozen encoding but the disagreement is a defect to report, not a choice
(`spec/README.md` §2). Every number below cites the Swift line that produced it.

**Normative** (a second renderer must match within §10.3):

1. The view input tuple and the frozen `BotFishView` API (§2).
2. Clip periods/durations/static flags (§4) and the phase/progress derivation
   (§5.1).
3. The default `BotFishParams` values and every per-state assignment, including
   the `expressiveMotion` overrides (§5.2–§5.3) and the lively clip sets (§5.4).
4. The controller: spring roots/substeps, face keys, blink/idle/lively timers,
   poke, one-shot/expression overlays, static sampling, zeroing and
   `needsAnimation` (§6).
5. The view-level amplification, pose quantisation and alpha quantisation
   (§7). The trajectory's `params` are the raw state-machine output; `pose` and
   `alpha` include §7.
6. Sprite order and the cel index rule (§8.1), the 256-entry tint LUT and the
   resolved layer paths (§8.2–§8.3).
7. The frame-clock ceilings and pause rules (§3).
8. The trajectory shape, case inventory, comparison rules, tolerances and
   regeneration command (§10).

**Renderer detail — not numerically gated** (a port should match it visually
but this contract does not claim pixel parity): the Core Graphics/SwiftUI
rasterisation, Bézier paths for eyes/brows/mouth/fins/decorations, stroke
widths, antialiasing, crown shadow, image interpolation, layer-cache keys,
cache size buckets, exact class names, and the 8 px head-slice compositing
(also an open CCR, §11.1). Screenshots are a regression aid, never cross-end
pixel parity.

## 2. Frozen inputs

### 2.1 View API

The iOS façade is frozen at `examples/probe-app/PhoneDSHProbe/Bot/Fish/BotFishView.swift:19-66`:

```swift
BotFishView(state: BotFishLifecycle, size: CGFloat,
            appearance: BotFishAppearance = .classic,
            crowned: Bool = false,
            still: Bool = false, allowsPoke: Bool = false,
            reaction: BotFishReaction? = nil,
            motionProfile: BotFishMotionProfile = .standard,
            workStyle: BotFishWorkStyle = .generic)
```

`size` is in points and must be `>= 1`; the view uses `side = max(1, size)`
(`BotFishView.swift:68`). `crowned` changes the cached base layer and the crop
(it is not just a visual overlay). `still` is the static/gallery mode; it is
distinct from reduce-motion. `allowsPoke` only gates the tap gesture
(`BotFishView.swift:138-144`); it never changes the model. `reaction` is the
Agent-driven cosmetic overlay and is deduplicated by `id`
(`BotFishEngine.swift:543-552`). `motionProfile` is fixed per view in production:
`.lively` is only the Bot status line, `.standard` everywhere else. `workStyle`
is an app-only `.working` sub-style and is ignored by `.standard`.

The frozen runtime value types are:

* `BotFishLifecycle` — **42** cases, not 41
  (`Sources/PhoneDSHBot/Avatar/BotFishDirector.swift:5-14`; the brief's “41
  cases” is stale). Raw values are the strings in §4; `shakingHead` =
  `"shaking-head"`, `highFive` = `"high-five"`, `poweringDown` =
  `"powering-down"`.
* `BotFishOneShot` / `BotFishDirectorState` — the director is frozen separately
  in `spec/bot/v1/golden/fish-director.json`; this contract consumes the
  lifecycle it produces and does not redefine priority/TTL.
* `BotFishReaction` — `id`, optional `botID`, `kind` (`action` | `expression`),
  `name`, `startedAt`, `durationMs` (`Sources/PhoneDSHBot/Avatar/BotFishReactions.swift:74-97`).
  Actions have 16 names and fixed durations (`:28-44`); expressions have 8 names
  and a 4 000 ms TTL (`:18-23`). `durationMs` is clamped to `>= 1`.
* `BotFishAppearance` — 15 colours (`BotFishAppearance.swift:10-26`, hex table
  `:27-44`) × 4 hairstyles (`:72-77`). `.classic` is `blue` + `long`
  (`:116`).
* `BotFishMotionProfile` — `standard`, `lively`; `BotFishWorkStyle` —
  `generic`, `reading`, `searching`, `running`, `writing`
  (`BotFishMotionProfile.swift:14-34`). Neither is a lifecycle state.

### 2.2 Fixture inputs (one trajectory case)

A case is the tuple

```
(state, appearance, crowned, still, reduced, motionProfile, workStyle,
 reaction | poke event | none, seed, viewport = (sizePt, displayScale),
 dtMs, steps, sampleSteps)
```

The fixture never calls a system RNG. The harness consumes a 32-bit LCG seeded
by `seed` (`state = (1664525*state + 1013904223) mod 2^32`,
`value = state / 2^32`) and records the **consumed prefix** in
`case.randomValues`. A consumer may use that array directly instead of the
LCG; it must consume values in call order and must not need more than the
array provides. `check_fish.py` verifies the array is exactly the LCG prefix
of `seed`.

The fixed grid is `dtMs = 1000/60` (16.666… ms) for every case. Events are
applied by `BotFishEngine.configure` *before* `step`, so an event with
`startStep = n >= 1` takes effect at the machine clock `(n-1)*dt`; step 0 has
`dt = 0` and starts at 0. `reaction.startTimeMs` records that clock, not
`startStep * dt`. This is why the replay's 1 000 ms `celebrate` event has
`startStep = 61` and `startTimeMs = 1 000`.

### 2.3 Viewports used by the golden

| Purpose | sizePt | displayScale | pixelSide | boost |
| --- | --- | --- | --- | --- |
| ordinary cases, crowned case | 64 | 2 | 128 | 1.0 |
| small standard cases | 32 | 3 | 96 | 2.2 |
| lively cases | 28 | 3 | 84 | 1.0 (lively clips are pre-calibrated) |

`pixelSide = ceil(sizePt * displayScale)` (`BotFishRenderer.swift:189-191`).

## 3. Frame clock and freeze rules

### 3.1 Requested frame ceilings

`BotFishView.frameInterval` (`BotFishView.swift:89-92`):

| Profile / size | Requested interval | Ceiling |
| --- | --- | --- |
| `.lively`, any size | `1/30` s | 30 fps |
| `.standard`, `size <= 40` pt | `1/15` s | 15 fps |
| `.standard`, `size > 40` pt | `1/20` s | 20 fps |

The view passes this to `TimelineView(.animation(minimumInterval:))`
(`BotFishView.swift:109`). It is a requested ceiling, not a promise of
delivery; the OS may coalesce frames. The trajectory does **not** use this
clock: it steps the state machine with a fixed `dt` so the model output is
reproducible. A renderer may draw at any real cadence as long as it samples the
same model at the same logical times.

The `BotFishStateMachine` itself has no fps and no pause flag: `playing` is a
constant `true` (`BotFishEngine.swift:70`). Pause is a view concern; a paused
view stops calling `advance`, so the machine stops.

### 3.2 Hard pause

`hardPaused` is true if any of these holds (`BotFishView.swift:73-83`):

1. the environment key `botFishPaused` is true — the Bot tab is off-screen or
   the app is not active (`BotFishView.swift:205-217`; the comment at `:74-78`
   documents the producer);
2. the view has not appeared (`isVisible == false`, `:125-130`);
3. `still` is true;
4. `accessibilityReduceMotion` is true (`:40`);
5. `ProcessInfo.isLowPowerModeEnabled` is true (`:45`, refreshed on
   `NSProcessInfoPowerStateDidChange`, `:131-134`).

While hard-paused the body renders `frozenFrame ?? engine.currentFrame`
(`:106-107`). `.task(id: pauseTaskID)` (`:96-102`, `:135-137`) re-runs when a
pause condition, lifecycle, appearance, crown, still, reduce-motion,
displayScale, low power, visibility, reaction id, profile or work style
changes. `syncPauseState` (`:184-202`):

* not paused → `engine.resetClock()` (next `advance` has `delta = 0`) and
  `frozenFrame = nil`;
* paused but not visible → keep `engine.currentFrame`;
* paused and visible → call `engine.advance` exactly once and keep that frame.
  If no frame has ever been produced, the fallback is `Image("BotAvatar")`
  (`:169-174`), not a fish frame.

A paused/backgrounded/low-power/reduced/still avatar therefore contributes
**no samples at all** after its one frozen frame. Resuming resets the delta to
0; it does not replay the missed interval.

### 3.3 Per-step delta

`BotFishEngine.advance` computes `delta = min(100, max(0, (now - last) * 1000))`
and the first advance has `delta = 0` (`BotFishEngine.swift:555-567`). The
state machine additionally clamps `dt` to `0...100` ms and clamps each spring
substep to `<= 1/120` s (`BotFishEngine.swift:291-296`,
`BotFishModel.swift:714-724`). Wall-clock jumps over 100 ms are therefore
truncated, not replayed.

### 3.4 `still` vs reduce-motion

`still` is passed to the engine as `isStatic`; reduce-motion as `reduced`.
Both freeze the sampling clock at 650 ms (`BotFishEngine.swift:320`), snap the
face and gaze springs to their targets, and zero head/body travel
(`:356-379`, `:413-418`). Reduce-motion additionally zeroes hair/ear/pose/
morph/fin-wave and whole-fish x/y/roll/sx/sy (`:419-430`). `still` alone keeps
the sampled pose values (e.g. a bowing reaction at its static beat still
displaces y) but does not animate them. The tap gesture is disabled when
`still` (`BotFishView.swift:138-144`).

A `.poke` transition is sampled before the `stateTime` freeze branch
(`BotFishEngine.swift:318-335`): a director-issued `.poke` still plays its
420 ms clip under `still`, although the view's gesture cannot produce one. The
fixture records this if a case exercises it; the current case inventory uses
`state = .poke`, not a frozen poke.

## 5. Model sampling

### 5.1 Phase and progress

`BotFishModel.sample(state:time:)` (`BotFishModel.swift:186-446`):

```
phase    = period  ? (time mod period) / period : 0        // period 0 -> 0
progress = duration ? clamp(time / duration, 0, 1) : phase
s        = sin(2π * phase)
```

`phase` and `progress` are stored in the params. `expressiveMotion`
recomputes its own `phase` from the same clip (or a fallback period, §5.3) and
uses `s2 = sin(4π * phase)` for a few states.

### 5.4 `expressiveMotion` overrides

`BotFishModel.expressiveMotion` (`BotFishModel.swift:449-697`) runs after the
base switch for **every** state. It first clears `eyeArt`/`mouthArt`,
`finFold`, `hairSway`, `earFlutter`, `puff`, `breath`, then applies:

```
period = BotFishClip.forState(state).period ?? special
special = 2400, except happy 2200, laughing 900, sad 3600, angry 2400,
          waving 1600, dancing 1800
phase  = period == 0 ? 0 : (time mod period) / period
s = sin(2π phase), s2 = sin(4π phase)
```

(The fallback only matters for states with no period; none of them has an
override below, so the observed `phase` is the clip phase for every override.)

### 5.5 Lively clips (`.lively` only)

`BotFishLivelyMotion.sample(state:workStyle:elapsed:)`
(`BotFishLivelyMotion.swift:342-368`) returns a complete params object with
`isLivelyMotion=true` for `thinking`, `working`, `streaming`, `speaking`,
`celebrate`, `done`; every other state returns `nil` and keeps the §5.3 model.

still applied on top (`BotFishEngine.swift:336-354`). `elapsed` is
`stateTime` (650 ms when still/reduced).

Track interpolation (`BotFishLivelyMotion.swift:26-68`):

```
q = elapsed / period
for a loop:   p = q - floor(q)                 // 0...1 inside the clip
for a one-shot: t = clamp(q, 0, 1)             // holds the last key
segment [a,b]: eased = smooth((p - a.phase) / (b.phase - a.phase))
value = a.value + (b.value - a.value) * eased
```

Keys are sorted, start at phase 0, end at phase 1, and the first/last values
match for loops. `BotFishLivelyTrack.zero` is `[(0,0),(1,0)]`.

## 6. Controller (springs, timers, overlays)

Source: `BotFishStateMachine` in `BotFishEngine.swift:61-486`. The trajectory
drives this class directly; the Android port must reproduce it, not just
`BotFishModel.sample`.

### 6.1 Spring

`BotFishSpring` (`BotFishModel.swift:702-728`) is critically damped and is
stepped in substeps of at most `1/120` s:

```
left = clamp(dt, 0, 0.1)
while left > 1e-8:
    h = min(left, 1/120)
    velocity += (-2*omega*velocity - omega*omega*(value-target)) * h
    value    += velocity * h
    left     -= h
settled = |value-target| < 0.0002 && |velocity| < 0.0002
```

`dt` is seconds (the machine receives milliseconds and divides by 1000 for the
springs). The omega roots are:

| Spring(s) | Omega | Source |
| --- | --- | --- |
| gazeX, gazeY | 23 | `BotFishEngine.swift:87-88` |
| headX, headY | 8 | `:89-90` |
| bodyX, bodyY | 5 | `:91-92` |
| morphX, morphY | 13 | `:93-94` |
| each face key | 22 | `:283-288` |
| lively pose x/y/roll/scale | 18 | `BotFishLivelyMotion.swift:79`; `BotFishEngine.swift:76-80` |

The 16 face keys, in this order (`BotFishEngine.swift:12-15`), are `eyeL,
eyeR, joy, browL, browR, anger, sorrow, smile, mouth, mouthWidth, round,
blush, tears, love, gazeX, gazeY`. Each face spring is created lazily with
`initial = target` and then tracked.

### 6.2 Per-step order

`step(dtMilliseconds)` (`BotFishEngine.swift:291-463`):

1. `time += clamp(dt, 0, 100)`; `elapsed += dt` while playing and not static
   (`playing` is always true; §3.1).
2. Standard-only idle event: if `state == idle`, no reaction,
   `time-idleEntered >= 3000` and `time >= nextIdleAt` and playing/not
   reduced/not static, consume one random value; `< 0.6` → blink, otherwise a
   700 ms look override from `[(-0.8,0),(0.8,0),(0,-0.7)]` chosen by a second
   random; then re-arm the idle timer.
3. Lively-only blink: every state, if `time >= nextBlinkAt`, blink and
   re-arm.
4. Expire a reaction when `time - reactionStart >= durationMs`.
5. Compute `pokeAge`, `poking` (`0 <= age < 420`), `stateTime`
   (`650` if reduced/static else `elapsed`), the active action/expression, and
   choose the sampled state/time: poke first, then action lifecycle, else the
   view lifecycle. A lively sample replaces the base model when applicable.
6. Apply the expression overlay (face keys + eye/mouth art + puff; `love`
   also sets `decoration="hearts"`).
7. Step every face spring (`dt/1000`), writing the sprung value back.
8. Gaze target = `clamp((lookOverride ?? directGaze ?? (0,0)) + p.gazeX, -1, 1)`
   (same for Y); step both.
9. Head target: standard `= gaze`; lively `= clamp(gaze + p.headX, -2, 2)` /
   `clamp(gaze + p.headY, -1, 1)`. Step. Body targets = stepped head; step.
   Then `p.x += bodyX*1.6`, `p.y += bodyY*0.9`, `p.roll += bodyX*0.35`.
10. Blink: `age = time - blinkStart`; if `0 <= age < 260`,
    `q=age/260`, `blink = q<0.45 ? 1-q/0.45 : (q-0.45)/0.55`; then
    `p.blink = max(0.02, blink)`.
11. Morph springs target `morphTarget` (always `(1,1)` in the shipped code);
    step.
12. If reduced/static: `headX=headY=bodyX=bodyY=0`. If reduced additionally:
    `hairSway=earFlutter=0`, `x=y=roll=0`, `sx=sy=1`, `morphX=morphY=1`,
    `finWave=0`.
13. Lively pose springs target `p.x/y/roll/sx/sy`; snap them under
    reduced/static; step (this is the only place the lively pose is damped).
14. `artMix = (reduced||static) ? 1 : clamp((time-artStart)/180, 0, 1)`;
    `eyeArtPrev/mouthArtPrev` come from `artFrom` (the art at the last state/
    reaction change). `last = p`; return.

`needsAnimation` (`BotFishEngine.swift:465-485`) is true if: a reaction exists;
the current clip is continuous (playing, not reduced/static, not static clip,
and period != nil or elapsed < duration); an art cross-fade is in progress
(`time-artStart < 180`); a poke/blink window is open; a look override exists;
or any gaze/head/body/morph/face spring is not settled. The lively pose springs (x/y/roll/scale) are not part of `needsAnimation`; the lively clip period keeps the view animating instead. The view uses it
only as a scheduling hint; it is not a render contract.

### 6.3 Blink, idle look, lively blink

* Blink always sets `blinkStart = time` (`BotFishEngine.swift:279-281`). The
  shape above is used by both profiles.
* Standard idle: first arm at init is
  `time + 6000 + clamp(random,0,1)*6000` ms (6–12 s); the event re-arms after
  firing (`:130-134`, `:298-310`). It only exists for `.standard`, `idle`,
  no reaction, after 3 s in the state.
* Lively: first arm is `3000 + random*(5000-3000)` ms, in every state; after a
  blink it re-arms with another random (`:136-145`, `:311-315`). The lazy
  `updateProfile` call also re-arms both timers, which is why the first
  `advance` with `.lively` consumes two random values before the first step.
* `poke()` sets `pokeStart=time`, clears the blink and look override, and
  clears an *action* reaction (`:211-216`). It does not clear an expression.
* A reaction with kind `.action` also clears poke/blink/look when it starts
  (`:222-235`); an expression does not.

### 6.4 One-shots and expressions

`playReaction` (`BotFishEngine.swift:218-235`) requires
`value.lifecycle != nil` (the name must be one of the 42 raw values; the 16
action names and 8 expression names all are). It records `artFrom` from the
last frame, sets `reactionStart = time`, and for actions clears
poke/blink/look. TTL is exactly `durationMs`:

* actions: `waving 1600, bowing 2800, clapping 1200, kiss 2600, cheering 1600,
  shy 3200, smug 2600, crying 2400, sighing 3600, shaking-head 2400,
  stretching 4200, yawning 4800, high-five 2200, nod 2000, celebrate 1500,
  dancing 1800` (`BotFishReactions.swift:28-44`);
* expressions: 4000 (`:23`).

An **action** replaces the whole sampled lifecycle (`sampledState =
action.lifecycle`, `sampledTime = age`) (`BotFishEngine.swift:329-335`). An
**expression** keeps the base body but overwrites the 16 face keys, `eyeArt`,
`mouthArt` and `puff` from the expression lifecycle; `love` additionally sets
`decoration="hearts"` (`:341-354`). Both use `reactionSampleTime` when
still/reduced:

| Condition | Action sample time | Expression sample time |
| --- | --- | --- |
| normal | `max(0, time - reactionStart)` | same |
| still or reduced | `max(1, durationMs * staticActionPhase[name])` | `650` |

`staticActionPhase` (`BotFishEngine.swift:259-265`): `waving .25`,
`bowing .50`, `clapping .125`, `kiss .50`, `cheering .25`, `shy .50`,
`smug .50`, `crying .50`, `sighing .60`, `shaking-head .125`,
`stretching .50`, `yawning .50`, `high-five .50`, `nod .25`, `celebrate .25`,
`dancing .25`; unknown names default to `.25`.

The engine deduplicates by reaction `id`: a SwiftUI rebuild with the same
`BotFishReaction.id` must not replay it (`BotFishEngine.swift:543-552`). A
different id starts a new overlay even if the same name.

## 7. View-level amplification, pose and alpha

These are applied by `BotFishEngine.advance` (`BotFishEngine.swift:555-667`)
after `step`. The trajectory's `params` are pre-amplification; `frame.view`
records the effective boost; `frame.pose`/`frame.alpha` are the real output.

### 7.1 Motion boost

`BotFishRenderer.motionBoost(for:)` (`BotFishRenderer.swift:193-199`):

```
size <= 40          -> 2.2
size >= 64          -> 1.0
40 < size < 64      -> 2.2 + (1 - 2.2) * ((size-40)/(64-40))
```

If `params.isLivelyMotion`, the boost is 1 regardless of size (lively clips are
pre-calibrated for 28 pt). Otherwise, when `boost > 1`:

```
x    = clamp(p.x * boost, -20, 20)
y    = clamp(p.y * boost, -20, 20)
roll = clamp(p.roll * boost, -9, 9)
```

`motionBoostMaxTranslation = 20`, `motionBoostMaxRoll = 9`
(`BotFishRenderer.swift:126-130`). `params.motionScale` stays `1` in the raw
state-machine output; `frame.view.motionScale` is the effective value.

### 7.2 Pose quantisation

With `size = max(1, sizePt)`, `target = pixelSide = ceil(size*displayScale)`,
`cropSide = crowned ? 448 : 416`:

```
pixelScale     = target / cropSide
pointsPerPixel = max(1, size) / target
offset(v)      = round_to_0.25( v * pixelScale ) * 0.25 * pointsPerPixel
scale(v)       = round_to(0.5/target)( v ) * (0.5/target)
roll           = round_to_0.1( roll )
```

`round_to(q)(v)` means `(v/q).rounded()*q` with Swift `rounded()` = nearest,
half away from zero. Pose fields:

```
offsetX = offset(boosted x)
offsetY = offset(boosted y)
roll    = round(boosted roll / 0.1) * 0.1
scaleX  = quantise(p.sx * p.morphX, 0.5/target)
scaleY  = quantise(p.sy * p.morphY, 0.5/target)
```

`offsetQuantum = 0.25`, `rollQuantum = 0.1`
(`BotFishEngine.swift:513-514`, `:643-663`). The offset is in points; the
pivot is source `(256, 350)` inside the crop, i.e.
`(0.5, 320/416)` normal or `(0.5, 340/448)` crowned (`BotFishView.swift:177-181`).
The golden's `geometry` carries these values; `check_fish.py` recomputes every
pose from the frame's own params and boost and requires `<= 1e-6`.

### 7.3 Alpha

`alpha = clamp(p.alpha, 0, 1); quantise to 1/64`:
`(clamp(value,0,1) * 64).rounded() / 64`
(`BotFishEngine.swift:665-667`). Alpha is not affected by the motion boost.

### 7.4 Layer/composition order (reference; renderer detail)

`prepare` builds two display-sized images (`BotFishRenderer.swift:219-280`):

* **base** (cached by hairstyle/colour/crowned/target): tinted body, `fixed`,
  then the crown overlay when `crowned` (`:389-428`);
* **face** (rebuilt when the quantised face signature changes): blush, left
  eye, right eye, mouth, tears, left fin, right fin, decorations, then brows if
  `eyeArt == nil` (`:480-512`).

The view draws base then face in a `ZStack`, applies scale/rotation/offset
around the pivot, then opacity (`BotFishView.swift:149-168`). Head slicing (for
`size > 40`, or `>= 24` for lively; `BotFishEngine.swift:587-590`) is a per-row
displacement of both layers.

### 7.4.1 Head-slice quantum (normative, FISH-1)

The active profile selects one quantum for the whole head-slice path:

| Profile | Quantum (source units) | Minimum size |
| --- | --- | --- |
| `standard` | 0.1 | `size > 40` pt |
| `lively` | 0.25 | `size >= 24` pt |

For each of `headX`, `headY`, `hairSway`, `earFlutter`:

```
levels      = round(value / quantum)      // Swift rounded(): half away from zero
displacement = levels * quantum
```

The quantiser and the restore MUST use the same profile quantum; `SliceKey`
carries the quantum, not a rounded tag. `standard` therefore restores
`0.1 * levels` and `lively` restores `0.25 * levels`; a lively level of 1 is
0.25 source units, not 0.1. The row weights (`headWeight`, `hairSway` and
`earFlutter` falloff) stay renderer detail; the frozen numbers are the quantum,
levels and displacement. `trajectory.json#headSlice` carries one case for each
profile, a half-away-from-zero case, an identity case, and the same raw input
under both profiles so the two quanta are directly comparable.

### 8.2 Tint LUT

`body.png` is an RGBA file whose samples are greyscale (SOURCES.md:13); the
renderer tints it with a 256-entry LUT built from the Bot colour
(`BotFishAssets.swift:30-96`). For each colour hex `#RRGGBB`:

```
rgb   = [R,G,B]
shade(amount, white=0) = [round(channel*amount + (255 - channel*amount)*white)]
stops = [
  (0.00, [13,15,25]),
  (0.20, shade(0.25)),
  (0.48, shade(0.52)),
  (0.73, rgb),
  (0.91, shade(1, 0.36)),
  (1.00, shade(1, 0.73)),
]
for i in 0..255:
  x = i/255
  find the first stop c>=1 with x <= stops[c].at; lower=stops[c-1], upper=stops[c]
  t = (x-lower.at)/(upper.at-lower.at)
  lut[i*3+ch] = clamp(round(lerp(lower.rgb[ch], upper.rgb[ch], t)), 0, 255)
ink   = shade(0.22)
mid   = rgb
light = shade(1, 0.5)
```

`round` is Swift `rounded()` (half away from zero). The 15 hexes are the table in
§2.1: white `#FFFFFF`, brown `#9D6937`, red `#E5484D`, orange `#F76B15`, amber
`#FFB224`, green `#14C16F`, teal `#13B7A2`, blue `#1680F3`, purple `#8F59F9`,
magenta `#F93498`, gray `#8B8B8B`, black `#1C1C1C`, silver `#C9CBD1`,
peach `#F3B6A4`, sky `#7ED0E8`. The complete 15×768 LUT and the ink/mid/light
triples are frozen in `golden/trajectory.json.palettes`; `check_fish.py`
recomputes every entry from the formula and hex table.

Tinting itself is premultiplied-alpha aware: the source bitmap is premultiplied,
the code recovers straight luma as `min(255, R*255/A)`, indexes the LUT and
writes `LUT[channel]*A/255` back (`BotFishAssets.swift:259-288`). Fully
transparent pixels stay 0. A port may use straight alpha internally as long as
the composed RGB matches; the LUT values, not the bitmap plumbing, are
normative.

### 10.3 Comparison and tolerances

* A missing/extra case or frame, a wrong `step`, a non-monotonic `timeMs`, an
  extra/missing param key, or a changed enum/art name/boolean is a failure.
* Numeric params, pose, timeMs and alpha compare with absolute tolerance
  `1e-6`. The values are IEEE-754 binary64 results of identical operations;
  the spring substep is 1/120 s and the longest replay is 300 steps, so an
  independent libm's `sin`/`cos` difference is far below `1e-6`, while the
  visible quanta are 0.25 output px, `0.5/target` scale, 0.1° roll and 1/64
  alpha. A tolerance of `1e-6` therefore cannot hide a one-quantum error and
  does not demand bit-identical libm behaviour. The checker's sharper pose
  audit recomputes the quantised values and requires `<= 1e-6`.
* `headSlice` levels are integers and compare exactly; `displacement` must be
  exactly `levels * quantum` (the checker uses `1e-12`, far below the 0.1/0.25
  quanta). A shared raw input under both profiles must produce different
  displacements, so a restored 0.1 for lively fails.
* Ordering: cases are in the fixed group order of §10.2, frames in increasing
  `step`. A consumer may compare by name rather than by array position, but
  must reject missing/extra entries.
* A second end must emit the same normalized shape. The Kotlin side can write
  `build/reports/fish-trajectory-android.json` and a comparator can diff it
  against this golden; the Android comparator is not yet implemented (D14
  follow-up).

### 10.4 Regeneration (the exact command)

```
python3 spec/ui/v1/bot/fish/tools/generate_trajectory.py --check
```

and to rewrite both goldens (review the diff before committing):

```
python3 spec/ui/v1/bot/fish/tools/generate_trajectory.py --write
```

The script does not re-implement the model. It creates a throw-away SwiftPM
package under the system temp directory whose executable target consists of
symlinks to the **original** app files
(`examples/probe-app/PhoneDSHProbe/Bot/Fish/BotFish{Model,Engine,Renderer,Assets,ImageCache,LivelyMotion,MotionProfile}.swift`)
and `tools/trajectory_harness.swift`, links the real `PhoneDSHBot` product from
this checkout, and builds for the iOS simulator:

```
swift build --package-path <temp> --triple <arch>-apple-ios17.0-simulator \
  --sdk "$(xcrun --sdk iphonesimulator --show-sdk-path)" \
  --scratch-path <temp-build> -c debug
xcrun simctl spawn <udid> <run-dir>/FishHarness --out <core.json>
```

The harness copies the asset tree next to the executable only as a runtime
bundle (iOS `Bundle.main` folder-resource behaviour, `SOURCES.md:24-32`); it
does not copy or modify the app source. `BotFishEngine`'s private machine uses
the system RNG, so the harness reads `params`/`needsAnimation` from a parallel
`BotFishStateMachine` driven by the recorded LCG and reads `pose`/`alpha` from
the engine. Every case is constructed so the engine's RNG can only affect blink
timing (face-only) or is never consulted: non-idle/standard cases take no idle
event, reaction cases end before the 6 s idle timer, and lively clips are
pose-identical regardless of blink. `--check` therefore reproduces byte-for-byte. `--check` compares both generated files
byte-for-byte and prints a unified diff. On a host without macOS/Xcode/an iOS
simulator it exits **77** with `SKIP`; that is not a pass.

`--core <file> --write` is a debug path for iterating on the metadata only; the
acceptance command is `--check` (or `--write` when intentionally regenerating).
